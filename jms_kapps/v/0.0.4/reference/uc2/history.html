jms_kapps.uc2.history#

The store’s history, from which a past possession is read: GraphDB’s history plugin (“data history and versioning”), and the one module that uses it.

A handover overwrites the box’s link to its possessor’s possession state, so the graph holds only the present possessor. Possession history lives in the store’s history mechanism, not in the graph: the history plugin records every transactional change at triple granularity, with the time of its transaction, and answers a query for the data as it was at one point in time, so that every past state can be read, as the paper’s requirements ask. The plugin is off by default.

This module is the vendor exception. The history plugin is GraphDB’s own feature, above the triple-store interface, and what is written here runs on GraphDB alone: the use case 2 reset may turn it on directly, and the interface gets no verb for it, neither the switch nor the reading. So the plugin’s IRIs are named here and nowhere else in the source, and the source check of the store’s own graphs lists this module as its one exception.

  • The switch. enable_history is what a launch with the option collect_history sends, the last step of its reset, after the reset loaded the ontology: the plugin’s update, with no filter, so the store records every change. Nothing in jms_kapps turns the collection off: a clear while it is off is not logged, and the cleared data then disappears from every earlier point in time. With the collection on, GraphDB refuses only a clear of the whole repository, which the reset never sends: it clears the default graph and each graph it loads by name. (Measured on the KIT GraphDB 10.8.5 on 2026-10-01.)

  • The reading. possessor_query is the query for the possessor of one box at one point in time, which docs/reference/past-possessions.md shows: the point is a graph of the plugin’s, in the server’s local time (server_time asks the server for it), and the query names its subject, the box, because a query that does not returns the live data. The plugin’s transaction IRIs are in UTC. Only a person, jms-uc2 trace-box and the live tests read the history: no participant does.

  • The change list. changes lists every change of one subject’s predicate, each with its transaction and its time, from the plugin’s change list (change_list_query). It reads each change, so a possession shorter than a second is in it too, which a point in time, to the second, can miss. Each change’s timestamp carries the server’s offset from UTC.

KIT runs GraphDB 10.8.5. The plugin’s own transaction IDs are used, never custom ones: 10.8.6 fixed major issues of the plugin with transaction IDs, and the default ones worked on 10.8.5.

jms_kapps.uc2.history.enable_history(db: TripleStore) → None[source]#

Turn on the store’s history collection, with no filter. The collection then records every change, until a person turns it off by hand.

Raises:

TripleStoreResponseError – If the store refuses it, as a store without the plugin may.

jms_kapps.uc2.history.history_enabled(db: Queryable) → bool[source]#

Whether the store collects history, as it reports.

jms_kapps.uc2.history.server_time(db: Queryable) → datetime[source]#

The server’s local time now, with its offset from UTC: SPARQL’s NOW(), as the server answers it. Its clock and its zone are the ones the plugin’s points in time are read in.

jms_kapps.uc2.history.point_in_time(moment: datetime) → IRI[source]#

The graph of the plugin’s that holds the data as it was at moment, to the second.

moment is the server’s local time, as server_time gives it. Its clock fields are taken as they are, whatever zone it names: the plugin reads them in the server’s zone.

jms_kapps.uc2.history.possessor_query(box: IRI, moment: datetime) → str[source]#

The query for the possessor of box at moment, the server’s local time: one row, the possessor, or none where the box had no possessor then.

It names its subject, the box, because a query that does not returns the live data (measured on the KIT GraphDB 10.8.5 on 2026-10-01). Its second pattern, the possessor’s link to its own possession state, never changes, so the live data answers it right either way.

jms_kapps.uc2.history.change_list_query(subject: IRI, predicate: IRI) → str[source]#

The query for every change of subject’s predicate: one row for each triple a transaction inserted or deleted, with the transaction, its timestamp, the object and whether it was inserted. The filter’s first two members, the range of time, are left open.
