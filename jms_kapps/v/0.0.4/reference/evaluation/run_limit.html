jms_kapps.evaluation.run_limit#

The run limit of the measurement harness: a run older than its limit ends as failed (over time), with the limit and the step at which the limit came: the series must run with no person present. Interim names.

Each step of a run has a limit of its own: a participant’s start, a workflow step, each store request of the harness, the warm-up and the window, the drain. The run limit is the limit of the whole run, so that a run that hangs between two steps does not stop a sweep until a person comes. A UC2 run of the bench launcher (bench), the store-only baseline and each replay level (baseline) have it, each with the same default, RUN_LIMIT_SECONDS.

What counts. The time counts on the run’s clock from the run’s start, where it reads the facts before the run, the moment before it creates its repository, to the start of the run’s end. The end itself, the stop of the participants, the deletion of the repository and the write of the record, is outside the limit: a UC2 run stops its limit before it stops its participants. So a run over its limit still cleans up and writes its record, and a run whose measurement is complete is never over time.

How it ends the run. A thread of its own looks at the run’s clock every LOOK_SECONDS. Once the run is older than its limit, it interrupts the main thread as a stop signal does (Platform.interrupt_main_thread): the run’s handler of the stop signals (run_and_end, through one_stop) raises OverTime there, between two steps of whatever runs there, and on POSIX also in a call that waits there. The run then ends through the end that a stop signal takes, and its outcome begins with OVER_TIME, “failed (over time)”, and names the limit and the step. A failed run is a result, so a sweep does not make it again. A stop signal that comes once the limit has come ends the run as over time too, and the limit does nothing once a stop signal has begun the run’s end. The end is certain, wherever the interrupt comes (run_and_end). A run off the main thread, where Python sets no signal handler, has no limit.

The limit is a run setting, outside the configuration’s key: the record keeps it under run_settings, as it keeps the other limits.

What the main thread of a run raises once the run is older than its limit. It is a KeyboardInterrupt, as a stop signal raises, so that every step lets it through as it lets a stop signal through, and nothing that catches an Exception keeps the run going. Its text is the run’s outcome.

jms_kapps.evaluation.run_limit.run_and_end(record: dict[str, Any], limit: RunLimit, steps: Callable[[], None], end: Callable[[], None], *, first_step: str, interrupted: str, add_action: Callable[[...], object]) → None[source]#

Run a run’s steps under its handler of the stop signals and under its limit, set the run’s outcome in record, and then run its end once, whatever comes when. A UC2 run of the bench launcher and a baseline both end so.

The outcome is completed where the steps return; OVER_TIME with the limit and the step (RunLimit.outcome) where the limit ended them, also where a cleanup of a step failed while the limit’s interrupt went through it, and then add_action adds RUN_LIMIT_REACHED; interrupted where a stop signal ended them; and failed: with the error where a step failed.

The end is certain. Python runs a signal’s handler after any instruction of the main thread, so a stop signal or the limit may raise its interrupt as the steps end, before the run has begun its end. The handler raises at most once (one_stop), and not once the run’s end has begun. So the end begins, its flag set, as the last step of the steps and as the first step after an error of theirs; an interrupt that comes before it is caught one level up, and sets the outcome. The end itself runs in a finally, where no interrupt comes any more.

Parameters:

  • record – The run’s record: its outcome is set here, before end runs.

  • limit – The run’s limit, which starts here, in first_step, inside the handler.

  • steps – The run’s steps, from its start to the start of its end. They mark each step on limit (RunLimit.at).

  • end – The run’s end: the stop of whatever runs, the deletion of its repository and the write of its record. A stop signal or the limit does not cut it short.

  • interrupted – The outcome of a run that a stop signal ended.

  • add_action – Adds an action to the run’s record, by its name and its details.
