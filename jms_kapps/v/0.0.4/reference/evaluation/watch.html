jms_kapps.evaluation.watch#

The server watch: from the load’s start to the drain’s end, the harness reads the server’s resource view and measures one round trip about every WATCH_INTERVAL_SECONDS, and keeps each sample with its time.

Other use of the same GraphDB may overlap a run, and the samples are what shows it: the CPU load, the heap and the round trip of the server across the whole run, not only at its start and end.

One request per view per interval. A sample is two requests, the resource view and the version (the round trip), and the next sample is one interval after the one before. A sample that takes longer than the interval skips the samples it missed, so that reads never pile up and a slow server is not asked more often.

Between the run’s own steps. Like the completion matcher, the watch reads where the run waits, not beside it: the run’s clock (WatchedClock) splits each wait at the time of the next sample, takes the sample, and goes on waiting. So a sample never runs beside the run’s own steps, and a test’s clock, which moves only when the run waits, drives it.

A read that fails never stops the run. A refused or lost read is kept with its status or its error, as the server’s views are. A sample that raises anything else is kept as a sample whose reads failed.
