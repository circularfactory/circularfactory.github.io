jms_kapps.evaluation.commit_table#

The tidy per-commit table and the replayed-writes table of the measurement harness, read from recorded run folders (interim names). The §7 figure script (evaluation/section_7/figure.py) reads them; each figure is a function of the two tables.

The runs. read_runs takes folders: an experiment’s store folders (<store>/heartbeats-<level>/runs/<run id>/), a bare runs folder, or a single run folder, and finds every record.json below them. Each record gets its labels:

  • the store: the name of a folder between the input folder and the run folder that is one of STORE_FOLDERS (kit, local), else the host of the record’s server;

  • the heartbeat level: off where the record’s run settings hold a heartbeat interval of null or 0, on where they hold another; else the name of a folder heartbeats-on or heartbeats-off above the run; else on, as every run before the heartbeat level was a setting ran with heartbeats on. A writes-only replay takes the level of the run it replays;

  • the arm: a run of use case 2 is KAPPS with SHACL on or off, by its configuration’s shacl; a baseline whose replay mode is “writes only” is the writes-only arm.

A run counts when it completed and is valid, as the harness’s table counts it. Left out, each with why: a record that cannot be read, a run of another kind, an all-requests baseline, a run that does not count, a writes-only replay whose replayed run is no SHACL-on run among the inputs, and every valid writes-only replay of a run but the earliest by its start (its record’s first action).

A commit is one span of the object-graph mapper’s commit (wrapper.COMMIT_SPAN). Its latency is the span’s duration; it is admitted when the span ended without an error; it is in the window when it started in the run’s measured window. Its store requests are the store-request spans below it, among the spans of its own participant, as the record’s commit link is made: a commit inside another commit is not walked into, its requests are its own.

The phases. Each store request inside a commit goes to exactly one phase, by the first rule that matches (request_phase): the checked write (an update that inserts a receipt) → update; a receipt query → receipt_ask; a receipt removal → receipt_removal; a read below the class-spec derivation, or a read of the schema/class category directly below the commit → class_query; a read below a fetch → fetch_reads; any other request → other_requests. A request’s phase takes its whole duration. Every other span below the commit gives its own time, its duration minus that of its children, to one phase (client_phase): class_derivation where it or a span above it (below the commit) is the class-spec derivation, else fetch_client where one is a fetch, else diff where one is the diff, else client_remainder; the commit’s own time is client_remainder. So a fetch inside a fetch counts once, under the outer one, and a class-spec derivation inside a fetch is class derivation, not fetch client. The ten parts are in whole microseconds, as the spans are, and sum to the commit’s latency exactly; none is below 0 where no span’s children overlap in time (interim choice: the own-time rule, in place of “the class-spec span minus its class-query reads”, which counts a class spec inside a fetch twice).

The kind of a commit, by its first checked write: heartbeat where the write names the heartbeat predicate in either spelling, else status: ` and the statuses it sets, else `other update; no write for a commit without a checked write. This is the rule the record’s kind follows where the record has it.

The writes-only latency of a commit is the latency of its replayed checked write: the replayed write whose commit is the commit’s span id and that inserts a receipt (the receipt’s removal carries the same commit and is not it; a heartbeat’s checked write is categorised a heartbeat update, so the pairing reads the receipt, not the category). A replay record without commit pairs by the participant and the recorded send time, which both records copy from the same record. Where a commit has several checked writes, their latencies are summed and the first’s send time is kept. The seconds since the window’s start are on the KAPPS run’s window and wall clock, for its commits and for the replayed writes alike.
