jms_kapps.uc1.page#

The page of a run of use case 1, which jms-uc1 serves.

The page says what to do, in three steps, and lists the five processes as use case 2’s Launcher lists its own: a row for each, with its state, its PID, its recent output on a click, and links to its API docs, its activity feed, its dashboard and its dashboard’s Logs tab.

One port for the run. The page passes every page of every process through its own port, under /p/<id>/, with the passthrough that use case 2’s Launcher uses (passthrough), and every link of the page, relative to the page, goes there. So over SSH, WSL or VS Code, forwarding the page’s port is enough. Every process takes a free port at each start, which a forward would have to follow. The server draws the page whole once, so that it shows the state at load without JavaScript. The script in static/page.js then asks /api/state every second and changes what differs, in place: the page never reloads itself. /api/state gives the same as JSON, for a test or a script.

Below the processes, the page lists the run’s unscrewing operations, each with the service that decided its outcome, the learned values, and the measured positions saved as uncertainty quantifications, each from one SPARQL query that it shows exactly as it was sent, with a copy button, as use case 2’s Launcher shows its query of the boxes. The queries run in a background read of their own (page_lists.PageLists), every second.

The switch “Save measurements as uncertainty quantifications” (interim name), at the head of the measured positions, shows and sets the anomaly detector’s mode. The page’s server holds no connection to the detector: it draws the switch off and disabled, and page.js reads and sets the mode on the detector’s own route (anomaly_detector.MODE_ROUTE) through the passthrough, like every other page of a process.

Everything the page shows comes from memory, the supervisor’s (Supervisor.snapshot) and the background read’s (PageLists.last), so a poll sends no request to the triple store.

The page links to “The UC1 sequence”, the paper’s scenario told step by step with the seeded names, which it serves itself at /sequence (sequence).

The page launches nothing and stops nothing: Ctrl+C at the terminal stops the run. What passes through to a process, a press of Unscrew and a change of the switch included, goes to the process’s own route. It binds a fixed port, PAGE_PORT, so a second jms-uc1 on the same machine is refused at its start, before it clears anything. Use case 2’s Launcher has port 8090, so both pages can be open on one machine.

The page takes the look of use case 2’s pages: its stylesheet carries the same colour variables with the same names and values, and its header carries the same logo. It imports nothing of use case 2, so the stylesheet and the logo are its own copies in static/; the passthrough is shared by both use cases in jms_kapps.common.

jms_kapps.uc1.page.links_of(child: ChildSnapshot) → list[dict[str, str]][source]#

The links of the row of child: PAGES, each as its label and its href through the page’s port, relative to the page (process_path). None until the process has an address, since nothing answers there before.

jms_kapps.uc1.page.address_block(page_address: str, children: Sequence[ChildSnapshot]) → str[source]#

The addresses of the run, for the terminal: the page, then the dashboard of each process in the order of children through the page’s port, or “no address yet” for one without an address. A process without a service has no pages at all: it is a device, such as the robot controller stand-in, which speaks only its protocol, and its row says so. Each process takes a new port at each start, so its own address would not stay; these do. The block starts and ends with a newline, so that a blank line sets it apart from the lines around it, and the names and addresses stand in two columns.

Operations, Learned values and Measured positions as /api/state gives them.

jms_kapps.uc1.page.render(children: Sequence[ChildSnapshot], lists: Lists | None = None) → str[source]#

One complete HTML5 page: the header, the section “What to do” with its three steps, the section “Processes” with the rows of children in the given order, and the sections “Operations”, “Learned values” and “Measured positions” with the rows and the queries of lists, empty without, the last with the switch of the detector’s mode and its credit. The stylesheet and the script are static/style.css and static/page.js, by relative paths, so that the page works under any path it is served at. Every value goes through html.escape.

jms_kapps.uc1.page.build_app(snapshot: Callable[[], Sequence[ChildSnapshot]], services: Mapping[IRI, IRI] | None = None, lists: Callable[[], Lists] | None = None) → FastAPI[source]#

The app of the page: / renders the snapshot, /sequence serves the page “The UC1 sequence”, /static serves the stylesheet, the script and the logo, /api/state returns the snapshot as JSON: for each process its name, state, PID, command line, recent output, address, dashboard, links, how long its state has been unconfirmed (or null), resource IRI and service class IRI (or null), and /p/<id>/ passes every page of each process through (passthrough), the process found in the snapshot by its id (process_of). No route reads the triple store: each calls snapshot alone. The passthrough’s pool of connections lives as long as the app’s lifespan, which PageServer runs.

With lists, the latest answers of the background read (PageLists.last), /api/state also gives Operations, Learned values and Measured positions (lists_json) and / renders them; without, all three are empty, as before the first read. Neither route sends a query: each calls lists alone. /api/state also gives mode_route, the detector’s mode route through the passthrough (mode_route_of), which page.js reads and sets.

class jms_kapps.uc1.page.PageServer(app: FastAPI, sock: socket)[source]#

Bases: object

Serves the app on a socket the caller bound, on a daemon thread. Its stop sets uvicorn’s should_exit and joins the thread.

start() → None[source]#

Run uvicorn’s server on a daemon thread, over the socket the caller bound. Off the main thread uvicorn sets no signal handler (uvicorn 0.53 capture_signals returns at once there), so the stop signals stay the caller’s — one_stop’s in jms-uc1.

stop(timeout: float = 5.0) → None[source]#
