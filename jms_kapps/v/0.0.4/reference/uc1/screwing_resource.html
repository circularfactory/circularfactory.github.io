jms_kapps.uc1.screwing_resource#

The screwing resource of use case 1: one attempt for each unscrewing operation, then the call of the anomaly detector.

It takes its work as the planner dispatches it. The planner creates an unscrewing operation, queued, which names one Screw and implements the screwing resource’s :UnscrewingCapability, and notifies the screwing resource, both with mw.issue_operation(). The middleware’s intake reads the operation once and runs the unscrewing workflow with it, one operation at a time. Nothing calls the workflow over REST. A notification of any other operation is logged and left alone.

One attempt is one commit of the middleware, mw.commit():

  • Entry: the operation is committed running. If the store refuses that, nothing runs, and the operation stays as it was.

  • Body: the attempt on the operation’s Screw, and the write of its frame into the time-series store. It holds nothing of the graph. Only transition.update(…) sets the operation’s time-series reference, for the exit.

  • Clean exit: the reference, and nothing else. There is no exit transition, so the operation stays running: the anomaly detector ends it.

  • Error in the body: the reference is dropped, and the operation is committed failed, with why as its svc:hasExecutionResult. The detector is not called.

The commit reads nothing: the intake has read the operation already.

A Screw type without its seven values ends the operation before the attempt. When the Screw type of the operation’s Screw holds one of the seven values (the six thresholds and the preparation turning angle) zero times, more than once, or not as a finite number, the screw cannot be unscrewed: in the real cell, the robot and the screwdriver need them. Then the screwing resource makes no attempt, writes no frame and calls no detector. It commits the operation from queued straight to failed, in one mw.commit(), with why as its svc:hasExecutionResult: it begins with NOT_ATTEMPTED and names each missing or unusable value. It commits no running first, because no work begins. The planner is notified of the end as of any other.

Then it calls the anomaly detector’s classify workflow with the operation’s IRI, found in the graph by the detector’s Classify capability (classify_call). That is a call inside the cell, and the screwing resource acts on no result of it: the detector ends the operation. It keeps the detector’s answer, how the detector left the operation, for its dashboard only.

A detector that is not reached leaves nobody to end the operation: no live detector is found, or the call fails or times out. Then the screwing resource ends the operation failed itself, in one mw.commit(), with why as its svc:hasExecutionResult (it begins with NOT_REACHED). The attempt’s curves and the operation’s reference stay. It reads the operation’s status first: an operation that is no longer running has been ended meanwhile, by a detector that took the call after all, and keeps its end: the record holds the status, result and outcome of that one read, not the call’s failure. The read and the commit are two steps, so an end that falls between them is still overwritten.

One attempt for each operation. An operation that is not queued when it reaches the workflow has had its attempt, or has ended, so it is logged and left alone.

The attempt is a function the screwing resource is given: the Screw and the values of its Screw type in, the frame of the attempt out. The intake reads the values with the operation, in the same fetch, from the Screw type that the Screw is linked to: the six thresholds and the preparation turning angle. The learner changes them on the type, so the next attempt on a Screw of that type is given the refined value. The attempt is always given all seven: without one, it is not made (above). The log line of each attempt and the dashboard show the values it was given. In jms-uc1 the attempt drives the robot over MQTT (robot_attempt): the middleware instance of the screwing resource is built with the robot’s wiring (build, with robot), so it holds a connector for each of the robot’s twelve parameters, built from the knowledge graph’s description of the robot and nothing else; the attempt writes the seven values and the start command through the write connectors, and collects every sample the robot publishes through the read connectors into the frame. The shipped demonstrator replaces only the robot controller: a stand-in process (robot_controller) that replays the example recording the demo names for the Screw (RECORDING_OF) over the same broker and topics. A robot that reports a failure, or none within the attempt’s timeout, raises, and the operation is failed with the reason. The replay attempts (replay_attempt, replay_by_screw) stay for a build without the wiring, as the offline tests and the detector’s live test have it.

Its activity feed is on, and so is the middleware’s state dashboard: the library’s own boxes, and the box “Attempts” in the tab “Screwing resource”, which the dashboard opens on (screwing_resource_dashboard). The box shows each attempt, newest first, from what the screwing resource keeps in its memory as it works (screwing_resource_memory): an open dashboard reads no store.

Run it as python -m jms_kapps.uc1.screwing_resource –dataset <name>. It starts and serves as every participant’s process does, through common.process, with the local InfluxDB unless INFLUXDB_URL names another. jms-uc1 starts it (run_core).

jms_kapps.uc1.screwing_resource.build(resource_iri: str, ogm: OGM, host: str, port: int, *, writer: FrameWriter | None = None, attempt: Callable[[IRI, Mapping[IRI, float]], Frame] | None = None, robot: RobotWiring | None = None) → SemanticMiddleware[source]#

The middleware instance of the screwing resource resource_iri, served at host:port, with its unscrewing workflow, its notification handler and its dashboard: the middleware’s boxes, and its own box in the tab “Screwing resource”, which it opens on.

With robot, the middleware is built to drive the screwing resource’s robot over MQTT: it reads the robot’s parameters from the graph under ROBOT_SCOPE, builds a connector for each from that description through use case 1’s binding descriptor, in a registry of its own, and brings up the broker through the wiring’s transport hook. The attempt then defaults to the MQTT attempt (robot_attempt.mqtt_attempt), whose setpoints are persistence writes through the robot’s write connectors (robot_binding.Setpoints). Nothing here names a broker, a port or a topic. The build raises if the graph does not describe every parameter of the robot.

Parameters:

  • writer – Where each attempt’s frame goes. Defaults to the InfluxDB that INFLUXDB_URL names, in the database jms-kapps.

  • attempt – The attempt on one Screw. Defaults to the MQTT attempt with robot, else to the replay of the recording success.

  • robot – The wiring that drives the robot over MQTT. None builds the middleware as before this wiring existed, with no connector: for a dataset without a seeded robot, as the offline tests and the detector’s live test have.
