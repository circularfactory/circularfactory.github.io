jms-kapps#

The two use cases of the paper KAPPS: A knowledge-based CPPS Architecture for the Circular Factory (arXiv 2605.22457), built on kapps-semantic-middleware, the semantic middleware of the KAPPS architecture’s reference implementation.

In the KAPPS architecture, the knowledge graph is the authoritative representation of the factory’s information state, and every change to it is validated against declared constraints before it is admitted. The parts of a Cyber-Physical Production System (CPPS) do not call each other at fixed addresses. Each part is a service (in the code, a participant: one process with its own middleware instance). A service registers in the knowledge graph, finds the other services there, and commits each change of the factory information state through the write path of its middleware instance. The triple store admits a commit only when it passes SHACL validation against the declared shapes, and otherwise refuses it in whole.

  • Use case 2: a decentralized conveyor network coordinated through a constraint-enforced knowledge graph. Each FlexConveyor module runs as its own service. A module reserves the next module for a box, conveys the box and hands it over. No central router exists: each module chooses the next module from the knowledge graph. Two faults that a person arms on a module make it commit a write that breaks a physical invariant, and the triple store refuses that write.

  • Use case 1: anomaly detection and learning in robotic unscrewing. Four services work on an unscrewing operation. A planner creates one operation per press of a button. A screwing resource records the time series of the attempt. An anomaly detector classifies the attempt. A learner refines a detection threshold of each screw type. The services coordinate through the knowledge graph and find each other there. The notifications and the call of the detector go over REST, to addresses that the knowledge graph holds; the time series are kept in InfluxDB. The screwing resource drives its robot over MQTT; a stand-in replaces the robot controller.

Both use cases are in one repository, because they share the demo seed that loads the ontologies and shapes, the triple store setup and the measurement harness, and because the paper cites them together. A launch loads the shipped ontologies and shapes into its dataset for the demonstration; a productive circular factory already holds them in its knowledge graph.

Run use case 2#

On Linux or macOS, with Docker and uv, the clone first, then in the repository root:

git clone https://github.com/circularfactory/jms_kapps.git && cd jms_kapps
docker compose up -d --wait   # a local triple store, with the datasets jms-kapps and kapps-demo, and an InfluxDB
uv sync --locked              # the packages, into .venv
export TRIPLESTORE_URL=http://localhost:7200 TRIPLESTORE_USERNAME=admin TRIPLESTORE_PASSWORD=root
./run-uc2

./run-uc2 seeds and launches the shipped topology cross, five modules, and then opens the Launcher page on http://127.0.0.1:8090/. It runs on the triple store that TRIPLESTORE_URL names; without that variable, it first starts the local triple store itself. It clears the dataset it runs on: jms-kapps, unless --dataset names another. A dataset is the triple store’s unit of data, one set of graphs. Every argument goes on to jms-uc2, as in ./run-uc2 --topology merge-fault-demo. Ctrl+C stops every process of the run.

The user guide has the full setup and shows what each page of a run holds.

What you see#

The Launcher page starts one process for each module of a topology, the modules of a station and their connections, plus the WarehouseManagementSystem (WMS), which spawns boxes and takes them back, and a monitor, which only reads the knowledge graph. It lists each process with its state, links to the dashboard of each, arms the two faults of each module, and launches another topology.

Open the WMS and spawn a box. The box travels from module to module to its destination. Each step of its journey is a hop: the giving module asks the next module to reserve itself, commits the handover, the change of the box’s possessor, and moves the box. The triple store admits or refuses each commit before anything moves. The monitor draws the station from the knowledge graph alone; with the Launcher’s checkbox “Collect the SHACL refusals in one monitor” ticked, it also shows each write that the triple store refused, with the shape that refused it.

Which facts the participants read from the knowledge graph, and which the demo gives them from outside, is in the page on the graph and the demo.

The glossary defines the words these pages keep (dataset, participant, hop, handover, heartbeat, deregister, stale, IRI, SSE and more) and maps the paper’s concepts to their instances in the use cases.

Run use case 1#

With the same setup as use case 2:

uv run jms-uc1

jms-uc1 seeds the two angle grinders of use case 1, starts its four services and the robot controller stand-in, and prints the address of the dashboard of each service, through the page’s port. It clears the dataset it runs on: jms-kapps, unless --dataset names another, and it refuses while another service is live there, unless --force. Its page, on http://127.0.0.1:8091/, shows each service and links to its dashboard. Every page of the run goes through that one port, so over SSH one forward is enough. Unscrew, on the planner’s dashboard, creates one unscrewing operation. Ctrl+C stops all five processes. jms-uc1 seed seeds once and prints the command line of each process instead, to run them by hand. See Use case 1.

What you see#

The planner opens one unscrewing operation for each press of Unscrew. The screwing resource sets the screw type’s values on its robot over MQTT, starts the attempt, and stores the samples that the robot publishes in InfluxDB; the robot controller stand-in publishes an example recording. The anomaly detector decides the outcome and commits it with its provenance. The learner refines a threshold of the Screw type from the attempts that ended ScrewIntact.

The first button of the page opens the planner’s dashboard. Press Unscrew there for Screw1: its attempt is intact, the outcome is ScrewIntact and the operation ends done. The page’s section Operations lists it with the anomaly detector as its deciding service; the detector’s dashboard lists the decision in its box Classifications; and the learner’s box Learner shows the new maximum dynamic torque of the Screw type M4, which the page’s Learned values shows as the latest value. The learner runs every 10 s, so wait for that change. Then press Unscrew for Screw2: it has no screw in it, the outcome is MissingScrew and the operation ends failed, with the reason ANOMALY: MissingScrew. Operations and Classifications show it; the learner learns only from ScrewIntact, so it changes nothing.

The detector’s decision on Screw2 uses the value the learner committed: Classifications shows the ten values of each decision, and the box Screw type values of the same dashboard shows what M4 held at the detector’s last read.

The user guide shows each page, and the lines of one operation in the logs.

On Windows#

./run-uc2 is a bash script, so the one command needs Linux, macOS or WSL. On Windows itself, start the local triple store with docker compose up -d --wait, set the three variables as The triple store shows for PowerShell or cmd.exe, and run uv run jms-uc2. Every process prints its command line in the form of the platform’s shell, so each also runs on its own there.

Requirements#

  • Python 3.12 or later. uv installs it where the machine has none.

  • uv. Do not use Poetry, and do not install into a global Python.

  • A triple store with a dataset that validates SHACL shapes. Where none is configured, docker compose up -d --wait brings a local one up, dataset included: see The triple store.

  • For use case 1, an InfluxDB 3. The same command brings a local one up: see Use case 1.

  • Three sibling packages from PyPI, pinned in pyproject.toml to their minor version and locked in uv.lock:

    • kapps-semantic-middleware 0.2.6 or later, the semantic middleware

    • kapps-triplestore-interface 2.2.2 or later, the triple store access module

    • kapps-ogm 0.3.2 or later, the Object–Graph Mapper (OGM)

Console scripts#

Script

Runs

jms-uc2

Use case 2 from a topology, behind the Launcher page. Clears the dataset it runs on, --dataset. See The Launcher.

jms-uc2 audit

Validates the whole of a dataset against both shape files of use case 2, the SHACL-SPARQL shape included, and prints the triple store’s validation report. Exits 0 when the dataset conforms. Reads only, --dataset. See Every rule refuses a write at commit.

jms-uc2 capability-resource

Shows the triple store refuse a capability that does not belong to exactly one resource: three writes, each printed with the triple store’s answer. Takes only a dataset named ogm-disposable-<id>, --dataset, and clears it; on a triple store that is not on this machine, set TRIPLESTORE_ALLOW_DESTRUCTIVE=1 for that one command. See Every capability belongs to exactly one resource.

jms-uc2 reachable-destination

Shows the triple store refuse, at commit, a write that breaks the SHACL-SPARQL shape of the reachable destination: four steps, each printed with the triple store’s answer and validation report. Takes only a dataset named ogm-disposable-<id>, --dataset, and clears it; on a triple store that is not on this machine, set TRIPLESTORE_ALLOW_DESTRUCTIVE=1 for that one command. See See the triple store refuse a rule that SHACL Core cannot express.

jms-uc2 trace-box

Runs use case 2 on four modules in a line, sends one box from Module1 to Module4, and prints every change of its possession, read back from the triple store’s history, one row for each transaction; writes the rows as JSON, --out. Exits 0 when they agree with the handovers the participants logged. Takes only a dataset named ogm-disposable-<id>, --dataset, clears it and turns its history collection on for good; on a triple store that is not on this machine, set TRIPLESTORE_ALLOW_DESTRUCTIVE=1 for that one command. See Read every change of a box’s possession back from the triple store’s history.

jms-uc1

Use case 1: seeds the two angle grinders, starts its four services and the robot controller stand-in, and prints the dashboard of each service; Unscrew is on the planner’s. Clears the dataset it runs on, --dataset. See Use case 1.

jms-uc1 seed

Seeds once, starts nothing, prints the command line of each service. Clears the dataset it runs on, --dataset. See Run use case 1 by hand.

jms-uc1 infeasible-operation

Shows the triple store refuse a planned unscrewing operation whose Screw’s Screw type lacks the values the attempt needs: it starts the use case, presses Unscrew on a Screw whose Screw type holds the values and on one whose Screw type holds none, prints the triple store’s answer to each with the validation report, and stops. Clears the dataset it runs on, --dataset. See See admission refuse a planned operation that the factory information state cannot carry out.

jms-eval-uc2

One UC2 run of one configuration of the measurement harness, on a dataset it creates and deletes, with its record.

jms-eval

One command from a spec of the harness to its report and table.

jms-eval-sweep

The runs of a spec, one by one, skipping a run whose record exists.

jms-eval-table

The numbers of the runs of a spec, as one table beside their records.

jms-eval-report

The report of the runs of a spec: tables and charts beside their records.

jms-eval-baseline

The baseline of one recorded UC2 run on the triple store alone.

jms-live-store

Development tooling: the token login, and the create, size and delete of a disposable dataset for a live check.

The jms-eval-* scripts are the measurement harness: see its README. A heavy run needs an approval that covers it; any person may approve.

Layout#

jms_kapps/
├── compose.yaml    the local fallback: a triple store, with the dataset created, and an InfluxDB
├── run-uc2         the one command of use case 2
├── docs/           the user guide, its screenshots, and the reference pages
├── evaluation/     the scripts of the paper's evaluation: section_7, its figures
├── graphdb/        the dataset's configuration
├── scripts/        the release's checks of this tree, which its continuous integration runs
├── tests/
└── src/jms_kapps/
    ├── common/     what both use cases use: the demo seed that loads the ontologies and shapes, the triple store setup, the process supervision
    ├── uc1/        use case 1, with its ontology and its recordings
    ├── uc2/        use case 2, with its ontology, its shapes, its topologies and its pages
    └── evaluation/ the measurement harness, which the use cases import nothing from

Each asset is below the package that uses it, so the wheel carries it, and an installed copy reads it with importlib.resources.

Development#

uv sync --locked
uv run pytest -m "not live"          # the offline tier: no triple store, no InfluxDB
uv run ruff check && uv run mypy
uv run pytest --dataset <name>       # with the triple store's variables set: also the tests that clear <name>

A test marked graphdb clears the dataset it runs against, so name a dataset that nothing else uses, never jms-kapps. See Tests.
