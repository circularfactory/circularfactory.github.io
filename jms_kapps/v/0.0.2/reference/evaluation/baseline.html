jms_kapps.evaluation.baseline#

jms-eval-baseline: the store-only baseline of one recorded UC2 run, on a repository of its own of the configured GraphDB, with its record. Iteration one of the measurement harness.

jms-eval-baseline <recorded run> [–runs <folder>] [–factor N]

[–heavy-run-approval <approval file> –spec <spec.toml>]

The baseline sends the store requests of a recorded run, whose record keeps their text (the observation, part 2 of the harness), straight to the store: the same mix of writes and queries, without KSM, the object-graph mapper or the triple-store interface on the way, at the same store size, beside the network’s round trip from the client host. It is a measurement store client, as the seed is, and no participant: it starts none. Its numbers stand beside the UC2 run’s (part 3).

A baseline run goes through these steps, in order, and records each action it takes with its time:

  1. Before anything (read_recorded_run, run_baseline). It reads the recorded run’s record, and refuses a run of the run kind uc2-unwrapped, which has no request text, any run kind but uc2, and a run that did not complete, which has no measures. It resolves the recorded run’s configuration, refuses a prefill file whose digest is not the recorded one, and, if the recorded run was heavy, or the factor is above 1, refuses to start unless an approval covers it (approval): the option –heavy-run-approval gives the approval file and –spec the spec, and the baseline runs only if the record of the replayed run holds a configuration key (a run made from a spec records it) that the approved spec lists, in the approval’s period. A replayed run whose record holds no key is refused. A baseline sends the recorded load at its recorded rate, so it is as heavy as the run it replays, and at a factor above 1 heavier. The record keeps the whole approval.

  2. The facts before the run, as part 1 keeps them: the client’s facts with the network’s round trip, the software’s versions and commits, and the server’s version, repositories and resource view (record, store).

  3. The store, through part 1’s store of a run: a repository of its own, eval- plus the run id, with the recorded run’s SHACL setting (store.create_run_repository); then the reset and the seed of the recorded run’s topology, its prefill file and its history collection, through the bench graph (bench.GraphDBBenchGraph, seed). This preparation uses the triple-store interface, and none of its requests is measured.

  4. The replay (replay), which logs in with its own credentials and replays no recorded login: first the requests recorded before the window, in their order, each after the answer to the one before, not measured; then the server’s views, and the window’s requests, each at its recorded offset from the window’s start, without waiting for an answer, until the window’s end. The requests recorded after the window’s end are not sent. Then it waits until each request of the window has its answer, or its error (the drain), and reads the server’s views again. The measured window lasts as long as the recorded one.

    Compressed in time (–factor, interim names). With a factor above 1 the window’s requests keep their order, and the offset of each, so each gap between two of them and the window itself, is divided by the factor: the same requests in a shorter time (replay_levels). A factor of 1, the default, is the replay as described above. Every factor above 1 is a heavy run and starts only under an approval that covers the replayed run’s configuration (below). The record of a baseline holds replay_level: the factor, the offered and the achieved rate per minute, the refusals and the timeouts, and whether the level is broken, with the signals.

  5. The end, also after a failure or a stop signal. It deletes its repository and no other (bench.delete_run_repository), and writes the record (record.write_record): the run kind baseline, the run it replays, and, for a completed run, its measures in the form of part 2’s (observation): every request it sent, those before the window too, as part 2 keeps them, so that a refusal among them shows; the window’s alone count, each with its offset and how late it left. As for a UC2 run, the deletion is a fact of its own in the record (repository_deletion), and the outcome says nothing of it: a baseline or a replay level whose replay completed is completed, with its measures and its level, also where the store did not delete its repository; the last line names such a repository.

The run limit (interim names). A baseline run, at every factor, has the run limit of a UC2 run (run_limit): 30 minutes by default, a run setting that the record keeps as run_settings.run_limit_seconds. The time counts from the facts of step 2 to the start of step 5. A baseline older than its limit ends through step 5, as a stop signal ends it, and its outcome is failed (over time), with the limit and the step at which the limit came: the facts before the run, the store or the replay.

Where KSM, the object-graph mapper and the interface are. The replay’s own module (replay) sends every replayed request with its own HTTP client, and imports none of them. This module prepares the store through the bench graph, which uses the interface, as the ticket allows, and reads the store’s answers with part 2’s readers (store_requests), so that a baseline’s request reads as a UC2 run’s does; they read text only, and send nothing.

Every request a replay sends goes to the baseline’s own repository, whatever repository the recording names, through part 1’s name guard. A recorded request’s media type is not in its record, so the baseline sends each as the triple-store interface sends it: a POST to a repository as a SPARQL query, and a POST to its statements as a SPARQL update, each accepting SPARQL’s JSON results; any other request goes with its method and its text alone. A UC2 run’s participants reach the store with these two and their login only.

Make one baseline run of recorded, on a repository of its own, and write its record. Returns the record, which is in record.json in the run’s folder too.

Parameters:

  • runs – The folder in which the run makes its own, named by its run id.

  • server – The configured GraphDB’s REST API.

  • graph_for – Prepares the run’s repository: part 1’s bench graph.

  • replay_for – The replay of the run’s repository.

  • clock – The run’s time: this machine’s if None.

  • approval – The covered record (approval.cover) of a heavy replay, or None where it is off. A heavy replay takes nothing else: the run checks that it names the recorded run’s configuration, and its period at the run’s start. A replay is heavy where the recorded run was, and at every factor above 1.

  • factor – The replay’s factor (replay_levels): the window’s offsets and length are divided by it. 1 is the recorded timeline.

  • sweep – What the record says of the sweep that made the run (the spec, the level’s key, the factor), or None for a run of the command.

  • echo – Where the run’s actions are printed.

  • watch_interval_seconds – The seconds from one sample of the server watch to the next: a run setting (watch). The watch runs from the window’s start to the drain’s end, as a UC2 run’s runs from the load’s start to the drain’s end.

  • run_limit_seconds – The limit of the whole run, in seconds of clock, as a UC2 run’s: a run setting (run_limit). A run older than it ends as failed (over time), at every factor.

Raises:

  • BaselineRefused – If factor is not a number from 1.

  • HeavyRunRefused – If the recorded run was heavy or the factor is above 1, and approval is not the covered record of its configuration, or its period is not the run’s start. Nothing is created, and no record is written.
