jms_kapps.evaluation.report#

jms-eval-report: the report of the runs of a spec, tables and charts, beside their records. Iteration one of the measurement harness.

jms-eval-report <spec.toml> [–runs <folder>] [–set KEY=VALUE …] [–seed N] [–resamples N]

[–live-checks <log>]

It reads the spec (spec), with each –set that the sweep was given, and the summary of every run below –runs (report_summary: a record is read once, and its summary kept beside it), and writes report/ into that folder: report.md, the tables and the charts for a person to read, runs.csv, configurations.csv, steps.csv, unanswered.csv and one PNG for each chart. It needs no store and no network, and runs nothing. The sweep makes it again after each run, whatever the run’s end (update_report).

The series (interim names). report.md, the chart titles and the chart labels show each configuration number with the spec’s series (spec.Spec.series), such as “before 7”, and a label that joins the number and the run kind, “after 7 unwrapped”; each CSV file keeps the number and gains a column series. The file names stay by number.

The report points (report_points; interim names) come after the tables and change none of their values: marks.csv (the hour of each run, whether it overlaps a live check of the log –live-checks names or the server watch shows other activity, its deadlock alarms and its dead heartbeats), hours.csv and one hours-<n>.png for each configuration, page_cache.csv, deadlock_alarms.csv and dead_heartbeats.csv. A mark says no data where the log, the server watch or the spans are missing.

The runs table has one row for each run: its configuration and the setting (topology, prefill, SHACL, strategies, box rate, wrapper), its run kind, its status and the reason, the transports ended per minute, the commits and their p50, p95 and p99, the p50 and p95 of the reads and of the writes, apart, the requests the store refused, those that timed out and those whose connection dropped, inside the window and outside it, apart, the stuck boxes, and the client host’s load in the window (below). The status is completed (a valid run), invalid (a check found it so), failed or interrupted. A failed or an interrupted run has no values.

The latencies are those of the accepted store requests of the window, logins left out, as jms-eval-table reads them; the reads and the writes are told apart by the request’s kind. A request that got no answer is counted in the column of the timed-out requests where its client gave up because the time ran out, and in that of the dropped connections where its connection closed, reset or failed before an answer (store_requests.unanswered_outcome; a request that a record written before says “timed out” is classified by its error, and an error of neither class, or none at all, counts as connection dropped). It is not among the latencies: its record keeps its real wait, the time until the failure, which is listed beside it (below).

The unanswered store requests (unanswered.csv, and a section of report.md): one row for each store request that got no answer, in the window and outside it, with its run, the place (in the window or outside the window), its outcome (timed out or connection dropped), its time, its wait in seconds (the real one) and its reason, the error as the record keeps it. A baseline run’s are listed too.

The client load (columns client_load, client_cpu_median_percent, client_cpu_max_percent and client_memory_max_gib of runs.csv, and a section of report.md): the median and the highest CPU use of the client host, in percent of all its CPUs, and its highest memory use in GiB, from the record’s samples (client_load) in the measured window. client_load says measured, no data (a record of the “before” series holds no sample, or none lies in the window) or not available (the host had no /proc); the report shows those words in place of the numbers.

The configurations table is the table of jms-eval-table (table.make_table), made from the same summaries in the same order with the same seed and resamples, so that its numbers are that table’s: one row for each configuration at its box rate and each run kind, over the runs that count, with each statistic of the table as columns.

The charts show the throughput, the commit p95 and the read p95 and write p95 of each configuration, a dot for each run (filled if valid, a ring if invalid) and a tick at the median of the valid runs; and, for each family of configurations that differ only in the size of their prefill, the throughput and the commit p95 against that size, on a log scale. A failed or an interrupted run is listed in the runs table and not plotted.

The steps (report_steps): steps.csv has one row for each configuration, role (WMS or module) and step, with the steps per minute, the median and the p95 seconds and the median size of the store’s answer, pooled over the valid runs’ spans in the measured window; for each family of prefill sizes, a steps chart compares the configurations step by step on a log time scale. The steps are read from the spans once, and kept in the run’s summary.
