jms_kapps.evaluation.bench#

The bench launcher: one UC2 run of one configuration, on its own repository, with its record.

A run goes through these steps, in order, and records each action it takes with its time:

  1. Before anything. A heavy run without an approval that covers it, now, is refused (approval); the record keeps the whole approval. The run takes its id, and its folder below the runs folder.

  2. The facts before the run. The client’s facts, the network’s round trip, the software’s versions and commits, and the server’s version, repositories, resource view, license, and the query and transaction view of every repository, the protected ones included (record, store). This is the run’s start: the moment before the harness creates its repository.

  3. The store. It creates its repository, eval- plus the run id, from jms_kapps’ repository config, with SHACL on or as the twin, and refuses a ruleset other than rdfsplus-optimized (store).

  4. The start, on the run core. The live-instance guard, then the run core’s start: its reset of the repository and the seed of the topology, through the bench graph, which then loads the prefill file and only then turns on the history collection, if the configuration collects history, so that the prefill is no history; then one process for each module and the WarehouseManagementSystem’s, with the configuration’s strategies, and no monitor. Between the prefill’s load and the first process, it reads the statement counts of its repository, where no participant writes. It waits at the readiness gate. Each participant’s output goes to its own file in the run’s folder.

  5. The warm-up and the window. It reads the WarehouseManagementSystem’s spawn rate workflow from the graph, and then sets the spawn rate through that workflow, the WarehouseManagementSystem’s REST interface, at the warm-up’s start, and to 0 at the window’s end. Load enters only there. The measured window starts when the warm-up ends; the server’s views are read just before it starts. A warm-up of 0 is a run without one: the views are read, and the window starts as the rate is set. From the load’s start the completion matcher reads the run’s ended transports at the configuration’s interval, until the drain’s end (matcher). The run’s transports are the ones that the WarehouseManagementSystem’s output names: right after the store admitted the create of a box, it logs that the box’s transport is queued, and the harness collects those lines as the run goes on (own_transports); telling them by a box number would read every box transport of the store at every read. Every read of the harness names the transports it asks for, in steps of at most READ_NAMES. The server watch starts with the load and samples the resource view and the round trip every WATCH_INTERVAL_SECONDS through the warm-up, the window and the drain (watch). The window’s start also reads the global page cache.

  6. The drain. It reads the run’s transports every DRAIN_POLL_SECONDS until none is open, or the drain bound has passed. The run’s transports are those the WarehouseManagementSystem’s log named as queued: the prefill’s past journeys are none of them, and the warm-up’s are. Then it reads each of the run’s transports, done with its place, failed with its place and why, or still open with its place, the matcher reads a last time, and the server’s views are read again, with the query view of every repository. From the warm-up’s start to the drain’s end the harness writes nothing to the graph: it only reads.

  7. The stop. It stops the participants in order (Supervisor.stop_all), and reads which services are still registered.

  8. The end, also after a failure. It stops whatever still runs, reads the statement counts again where no participant writes, deletes its repository and no other, counts the spawns the WarehouseManagementSystem refused from its output, and, for a run that completed, adds the observation’s measures and checks (observation); then it writes the record (record.write_record). A stop signal, Ctrl+C, SIGTERM or a closing terminal’s SIGHUP, ends the run there too, as interrupted; a stop signal while the run ends does not cut it short.

The deletion of the repository (interim names). The outcome says how the measurement ended, and only that: a run whose steps completed is completed, and gets its observation, whatever the deletion did; a failed, over-time or interrupted run keeps its outcome. The deletion is a fact of its own in the record, repository_deletion: deleted, why it was not, and answer_lost, why the deletion got no usable answer, where it got none; it is null where the run created no repository. Where the deletion gets no usable answer, since the request did not reach the store, no answer came in the request’s time, the connection dropped, a gateway in front of the store answered 502, 503 or 504 in its place, or an answer arrived but could not be read (the record says so, not that the answer was lost), one list of the server’s repositories, by a request that names none, says whether the store deleted it (GraphDBServer.deleted_after_a_lost_answer); where that list fails too, the repository counts as not deleted, with both whys. Any other answer is a refusal, with no list. A repository that the store did not delete is the action “repository not deleted”, with why, and the last line of jms-eval-uc2 and the line that jms-eval-sweep prints after the run name it (outcome_line), so that a person deletes it.

The run limit (interim names). Each step above has a limit of its own, and the whole run has one too: 30 minutes by default (run_limit.RUN_LIMIT_SECONDS), a run setting outside the configuration’s key, which the record keeps as run_settings.run_limit_seconds. The time counts from the run’s start, where step 2 reads the facts, to the start of step 7: the stop of the participants and the end are outside the limit. A run older than its limit ends through step 8, as a stop signal ends it: the participants stop, the repository is deleted and the record is written. Its outcome is failed (over time), with the limit and the step (2 to 6) at which the limit came, by the step’s name above, and its actions hold run limit reached (run_limit).

The observation. With the configuration’s wrapper, each participant starts through the wrapper (wrapper), whose spans go into spans/ in the run’s folder, one file for each participant; without it, the participants start as they are, and the record’s run kind is uc2-unwrapped. Either way each line of a participant’s output is stamped with the time it arrived, so that a deadlock alarm is dated.

Each run setting stays at the default of today’s use case 2, and the record holds each with its value: none is swept, except two that are keys of the configuration now, the transit time and the retry wait, and one that the configuration gives or the run fills in, the WarehouseManagementSystem’s pick seed (interim names). A run takes the seed of its configuration, or else repetition 1 of the default base seed (configuration.pick_seed), seeds the WarehouseManagementSystem’s picks with it, and writes it to its record and to the saved configuration, so that this configuration run again makes the same picks. Everything the run reaches outside itself comes through a port, so that a test runs it against stand-ins: the server (GraphDBServer), the graph (BenchGraph), the run core’s supervisor, the spawn rate (SpawnRate) and the clock (Clock).

jms_kapps.evaluation.bench.run(configuration: ~jms_kapps.evaluation.configuration.Configuration, *, runs: ~pathlib.Path, server: ~jms_kapps.evaluation.store.GraphDBServer, graph_for: ~collections.abc.Callable[[str, ~pathlib.Path | None, bool], ~jms_kapps.evaluation.bench.BenchGraph], spawn_rate: ~jms_kapps.evaluation.bench.SpawnRate, supervisor_for: ~collections.abc.Callable[[~jms_kapps.uc2.run_core.RunGraph, ~collections.abc.Callable[[str], None]], ~jms_kapps.common.supervision.Supervisor] = <function new_supervisor>, clock: ~jms_kapps.evaluation.bench.Clock | None = None, approval: ~jms_kapps.evaluation.approval.Covered | None = None, echo: ~collections.abc.Callable[[str], None] = <built-in function print>, sweep: ~collections.abc.Mapping[str, ~typing.Any] | None = None, watch_interval_seconds: float = 5.0, run_limit_seconds: float = 1800.0) → dict[str, Any][source]#

Make one UC2 run of configuration, on a repository of its own, and write its record. Returns the record, which is in record.json in the run’s folder too.

Parameters:

  • runs – The folder in which the run makes its own, named by its run id.

  • server – The configured GraphDB’s REST API.

  • graph_for – The run’s graph on a repository, by its name, with the prefill file it loads and whether its reset sets the shapes, the configuration’s shacl.

  • spawn_rate – Sets the WarehouseManagementSystem’s spawn rate.

  • supervisor_for – Starts the run core’s supervisor: new_supervisor.

  • clock – The run’s time: this machine’s if None.

  • approval – The covered record (approval.cover) of a heavy run, or None where it is off. A heavy run takes nothing else: the run checks that it names this configuration, and its period at the run’s start.

  • echo – Where the run’s actions and the supervisor’s notices are printed.

  • sweep – Which run of a sweep this is, for its record (jms-eval-sweep): its spec, its configuration’s number and key, and its repetition. None for a run of its own.

  • watch_interval_seconds – The seconds from one sample of the server watch to the next: a run setting (watch).

  • run_limit_seconds – The limit of the whole run, in seconds of clock: a run setting (run_limit). A run older than it ends as failed (over time).

Raises:

  • HeavyRunRefused – If the run is heavy and approval is not the covered record of this configuration, or its period is not the run’s start. Nothing is created, and no record is written.

  • WrapperUnavailable – If the configuration has the wrapper on and OpenTelemetry, the extra evaluation, is not installed. Nothing is created, and no record is written.

jms_kapps.evaluation.bench.read_statement_counts(record: dict[str, Any], key: str, repository: str, server: GraphDBServer, actions: Actions) → None[source]#

Read the statement counts of the run’s repository into the record under key, and say so in the actions, so that their order shows where it was read. The caller reads them only where no participant writes. A refused read is kept with its status and the run goes on.

jms_kapps.evaluation.bench.delete_run_repository(record: dict[str, Any], repository: str, server: GraphDBServer, actions: Actions) → None[source]#

Delete the run’s repository, which only this run created, and keep in record every request the harness sent to the server’s REST API. The store-only baseline ends the same way (baseline).

The deletion is a fact of its own in the record, repository_deletion: deleted, why it was not, and answer_lost, why the deletion got no usable answer, where it got none: the request did not reach the store, no answer came, or an answer came that could not be read. A repository that the store does not delete is an action of its own too, with why. The outcome says nothing of the deletion: it says how the measurement ended, and only that.

jms_kapps.evaluation.bench.outcome_line(program: str, record: Mapping[str, Any], runs: Path) → str[source]#

The line that tells how a run ended and where its record is below runs, and names its repository where the store did not delete it, so that a person deletes it: the last line of jms-eval-uc2 and of jms-eval-baseline, and the line that jms-eval-sweep prints after each run, each with its command’s name program.
