jms_kapps.uc2.strategies#

Who chooses where a box goes: the strategy of the modules and the strategy of the WarehouseManagementSystem, each chosen by its name when use case 2 starts.

Two kinds. A strategy is an object with a label, a person’s name for it. Its kind is its class and the entry-point group it is registered in; its name is its entry’s name, the one that jms-uc2 –module-strategy and –wms-strategy take.

  • A module strategy (ModuleStrategy) answers neighbours_to_ask: given the module, the box’s destination, the module the box came from (or none), the module reserved ahead for the box (or none), and the station’s connections as the module read them, each with its source, its target and its direction, it answers the neighbours the module asks, in order, at most two: the first, and the detour if the first declines; none where the box cannot go on. A module asks it wherever it chooses a neighbour: when it carries a box on, and at a look-ahead, where it asks the first. After a crash it is asked again, with the same signature: when a neighbour it named cannot be reached, or refuses “no live route on”, the module leaves that neighbour out for the box and asks again with the connections to each module left out removed and with no module the box came from, which is then a valid choice; at a look-ahead, the module that holds the box stays the module it came from. So real and every strategy that names only neighbours a connection leads to need no change for it.

  • A WMS strategy (WmsStrategy) answers origin_and_destination: given the candidates of a spawn (each free origin the spawn allows, with the destinations it allows that the origin reaches, narrowed to what the request names), the station’s connections as the WMS read them in the same read, and the WMS’s chooser, which picks one module out of several, it answers one candidate pair. The WMS asks it only where it picks.

A strategy only chooses: it never writes, never reads the store, and never waits. The module and the WMS read what they read anyway, and pass it in. Everything around the choice stays theirs: the look-ahead before a module accepts, the bound of a reservation, the waiting order, the stop rules, and what the store admits. So does what they make of an answer outside the contract: a module keeps the first two neighbours, and drops one to which no connection of it leads; the WMS refuses a spawn whose pair is not a candidate.

`real`, labelled “Real behaviour”, is one strategy of each kind, and is the demonstration’s behaviour: a module asks the module reserved ahead first, while a connection leads there, and otherwise the first module on a shortest path, and then the detour, which avoids the first and the module the box came from (routing); the WMS’s chooser picks the origin among the candidate origins, then the destination among that origin’s destinations. A synthetic strategy, one that makes traffic a benchmark can repeat, says so: its label ends in “(synthetic)”.

Finding strategies. Each kind has a Python entry-point group, declared in the pyproject of the package that provides it: jms_kapps.uc2.module_strategies and jms_kapps.uc2.wms_strategies. Each entry loads one strategy object, and the entry’s name is the strategy’s name; jms_kapps registers real in both. An entry whose module cannot be imported, as when the evaluation folder that holds the benchmark strategies is not there, is skipped with one WARNING; so is an object of the other kind, or of none; and of two strategies of one kind with one name, the first found counts, and one WARNING names the other. No registry holds strategies beyond the entry points. Use case 2 imports nothing from the evaluation folder, so the demonstration runs without it.

A strategy is chosen at start in the Launcher, for the WMS and for the modules; the default is the real behaviour.
