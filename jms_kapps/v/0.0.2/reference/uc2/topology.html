jms_kapps.uc2.topology#

The layout of a FlexConveyor: its modules, and which module each one hands boxes to.

A topology is the first iteration’s module list, the one format in which machines that run use case 2 exchange topologies: a JSON list of modules, as the first iteration of this use case (the paper’s artifact) wrote them. Each module is a JSON object with its id, the module’s IRI in fci:, and its properties under their IRIs, each IRI encoded as the OGM encodes a field name (IRI.lined), with a list of values:

[{"id": "http://w3id.org/circularfactory/FlexConveyorInstances#Module1",
  "http_c__s__s_www_d_w3_d_org_s_1999_s_02_s_22-rdf-syntax-ns_h_type":
      ["http://w3id.org/circularfactory/FlexConveyor#EntryModule"],
  "http_c__s__s_www_d_w3_d_org_s_2000_s_01_s_rdf-schema_h_label": ["Module 1"],
  "http_c__s__s_w3id_d_org_s_circularfactory_s_FlexConveyor_h_hasConnection": [
      {"http_c__s__s_w3id_d_org_s_circularfactory_s_FlexConveyor_h_connectsTo":
           ["http://w3id.org/circularfactory/FlexConveyorInstances#Module3"],
       "http_c__s__s_w3id_d_org_s_circularfactory_s_FlexConveyor_h_hasDirection":
           ["http://w3id.org/circularfactory/FlexConveyor#South"],
       "http_c__s__s_w3id_d_org_s_circularfactory_s_FlexConveyor_h_onPort": [0]}]},
 ...]

  • rdf:type holds the module’s types: fc:FlexConveyorModule, and the roles fc:EntryModule and fc:ExitModule, which are optional. A module that lists no type is a FlexConveyorModule, as the first iteration seeded it. Every type listed is written into the graph, where the first iteration’s seed kept the first and dropped the rest.

  • rdfs:label is optional. Without one, the pages show the module’s local name.

  • fc:hasTransitTime is optional: the module’s own transit time, a list of one number, the seconds it takes to convey a box. 0 is allowed and means that it conveys at once, with no wait. A module without one takes the transit time of its launch (seed.seed_topology).

  • fc:hasConnection holds the connections, each a node with the module it leads to (fc:connectsTo), its direction (fc:hasDirection: fc:North, fc:East, fc:South or fc:West) and its port (fc:onPort, 0 where none is given). A connection runs one way, as it is listed: a module that hands boxes back has a connection of its own. The first iteration’s seed added the way back of every link, which would make a topology that runs one way run both ways. A node’s own id, which some of the first iteration’s files give, is not taken: the seed names a connection by its module and its direction.

  • Every value is in a list, even where there is one. An IRI is written as a string or as {“id”: …}, as the first iteration wrote both.

  • A key that is none of these is refused, so that a misspelt one is not silently dropped.

parse_topology reads a module list, and Topology.module_list writes one. Every topology this package ships is one, below topologies/, and the first iteration’s files load as they are. In memory a topology is a Topology, which names each module by the local name of its IRI in fci:, so that it reads without prefixes; the Launcher page shows the running one in those terms.

The Launcher seeds the graph from a topology, and jms-uc2 –topology names one: a shipped one by its name, the stem of its file, or else a file by its path. The Launcher page names a shipped one, or sends a module list edited on it whole (edited_topology), never a path. The monitor builds no topology: it lays out the modules the graph holds, by their IRIs, with layout, the walk a topology’s places uses.

A topology that parse_topology accepts is one the graph accepts: every connection leads to a module of the same topology, and a module has at most one connection in each direction. No module takes the IRI of the WarehouseManagementSystem, which every run seeds and starts beside its topology. The monitor is the demo Launcher’s, so the Launcher refuses a module on its IRI, and a run without the Launcher, as a benchmark’s, may have one.

A topology that is loaded holds at least one module: with none, the WarehouseManagementSystem and the monitor would run and no box could be spawned, so loading a topology, shipped or from a file, or launching one edited on the page, refuses an empty module list with “a topology needs at least one module”. Only the load check refuses it: reading a module list, for the editor’s layout or an opened file, accepts the empty list, so that a person can edit it until it passes. A single module loads. Otherwise the editor’s “Empty grid” would pass the check and enable “Launch this”.

A topology that is loaded may hold no pure two-way corridor (routing.pure_corridor): a module whose only two connections both run both ways. Two boxes that meet head-on there, one each way, could wait for each other forever, with no neighbour to step aside to, so loading a topology, shipped or from a file, refuses one that has such a module, and names it and its two neighbours. Any other cycle of connections loads, two-way connections too: a module accepts a box only where the box can go on at once, and a box whose next module declines tries a detour first. Where a cycle could still hold boxes, the deadlock alarm is the visible backstop, which fails nothing.

Roles are optional (choices). A box starts on an entry module where the topology names any, and on any module where it names none; it ends on an exit module where the topology names any, and on any module where it names none; never on its origin. The WarehouseManagementSystem spawns by this rule and its form offers by it (entries_and_exits). The load check looks at no role. The shipped cross names Modules 1 and 2 as entry modules and Modules 4 and 5 as exit modules, and Module 3, in the middle, none; the grid, the tee and the pair name theirs. Roles are optional, as the first iteration’s WarehouseManagementSystem had them, and a module can be both. The monitor draws no hop strong: it maps destinations, not routes.

jms_kapps.uc2.topology.layout(connections: Mapping[Key, Sequence[tuple[Literal['North', 'East', 'South', 'West'], Key]]]) → dict[Key, tuple[int, int]][source]#

A cell on a grid for each module, found by walking the connections’ directions.

connections gives each module, by any key, its connections as (direction, module) pairs. The walk starts at the first module, and walks each connection from either end: the module it leads to lies one step in its direction, and the module it leads from one step back. So a one-way flow with several starts, such as the grid’s top row, is laid out whole. A module the walk does not reach, or whose cell is taken already, starts a part of its own: the walk lays that part out on its own, from the next module not yet placed, and puts it on the rows below the others, from the left edge. So a part never takes a cell of another, and a topology the page’s editor wrote opens again in it. A connection to a key that is not a module of connections is not walked, so a graph that is only partly populated still has a layout, and no module has none.

Where a box may start, its origins, and where it may end, its destinations, on the modules of types, which gives each module its types, in their order.

Roles are optional. A box starts on an entry module where the modules name any, and on any module where they name none; it ends on an exit module where they name any, and on any module where they name none. A module of both roles is both. Roles are optional, as the first iteration’s WMS had them.

exception jms_kapps.uc2.topology.TopologyRefused[source]#

Bases: ValueError

Loading refuses a topology: what is read is no module list, or one that cannot be seeded, or the load check refuses it. The message is the reason, for a person to read: the Launcher page shows it, and jms-uc2 –topology prints it. Every refusal of this module is one, so that a caller can tell a refusal from any other error, as a bug’s.

jms_kapps.uc2.topology.load_topology(name_or_path: str) → Topology[source]#

The shipped topology called name_or_path, or else the one in the file at that path.

A shipped name always means the shipped topology, whatever the working directory holds, so a file of that name cannot take its place. Such a file is reached by a path that is not a bare name, such as ./cross. Anything that is not a shipped name is a path, and only that file is read.

Raises:

  • UnknownTopology – If it is neither a shipped name nor a file, in the words of the check of a shipped name, which name the shipped topologies, and saying that there is no such file either.

  • TopologyRefused – If its topology cannot be seeded, naming why.
