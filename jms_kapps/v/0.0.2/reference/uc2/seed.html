jms_kapps.uc2.seed#

What use case 2 finds in the graph before any module starts.

Every module can give and take a box actively (mes:Pass and mes:Retrieve, the both-active pair of the middleware’s handover), and so can the WarehouseManagementSystem, which a launch seeds beside every topology: it creates each box on its origin and takes it back, so a box has a possessor all its journey, as Core’s exactly-one possession requires. It hands no box onto the station with the middleware’s handover, so its mes:Pass goes unused. The two-module seed has module 1, connected to module 2, and the WarehouseManagementSystem as an individual only, with no handover ability: no box goes back to it, and a destination module keeps each box.

jms_kapps.uc2.seed.shapes_document(*, sparql_shapes: bool) → str[source]#

The shapes that the store receives as one document: the Core file, followed by the SHACL-SPARQL file when sparql_shapes.

The store’s shapes_set replaces every shape, so two files must go as one document. reset adds the middleware’s operation-status shape in front of it.

jms_kapps.uc2.seed.reset_uc2(db: TripleStore, *, individuals: str = '', collect_history: bool = False, with_shapes: bool = True, sparql_shapes: bool = False) → None[source]#

Empty the dataset and load use case 2’s ontology and shapes, then individuals.

The shapes are set through the store’s shapes_set, so a dataset without SHACL validation refuses the reset, before it loads anything: shapes stored there would validate nothing. Only with with_shapes False does the reset send no shapes, and seed such a dataset without them: the measurement harness sets it for its SHACL-off twin, and nothing else does. The SHACL-SPARQL rule is loaded only with sparql_shapes, which the shape tests, the audit and the SHACL-SPARQL demo ask for and a launch does not.

With collect_history, the launch option, the reset then turns on the store’s history collection, with no filter, after it loaded the ontology: its last step (history.enable_history). Without it, the reset sends nothing to the history, neither on nor off, so a dataset whose collection an earlier launch turned on keeps collecting. Nothing else in the reset changes: with the collection on, the store refuses only a clear of the whole dataset, and the reset clears the default graph and each graph it loads by name. It never turns the collection off around a clear, because a clear is then not logged, and the cleared data disappears from every earlier point in time.

jms_kapps.uc2.seed.seed_topology(db: TripleStore, topology: Topology, *, transit_seconds: float, resources: Mapping[IRI, str] | None = None, collect_history: bool = False, with_shapes: bool = True, sparql_shapes: bool = False) → None[source]#

Empty the dataset, then seed every module of topology, the WarehouseManagementSystem, and each of resources. With collect_history, the launch option, the reset then turns on the store’s history collection (reset_uc2). With with_shapes False, the reset sends no shapes, for a dataset without SHACL validation; by default a dataset without it refuses the seed (reset_uc2). The SHACL-SPARQL rule is loaded only with sparql_shapes, which the shape tests, the audit and the SHACL-SPARQL demo ask for.

Every module gets exactly one fc:hasTransitTime: its own from the topology, else transit_seconds, the launch’s. Each of resources is a plain cfc:Resource with the label it maps to: a participant that the caller starts beside every run, as the demo Launcher starts the monitor. The run core starts no monitor, so the seed names none.

One import, so the triple store checks the modules and their connections together: a connection’s shape needs the module it leads to. It is the launch’s last import, and the reset registers the dataset’s prefixes after it. Its Turtle declares those prefixes, because the store keeps a prefix an import declares: left to itself, rdflib would declare names of its own invention, such as ns1:, for the registration to delete again.

jms_kapps.uc2.seed.possession_triples(db: TripleStore, box: IRI, possessor: IRI) → list[tuple[IRI, IRI, IRI]][source]#

The triples that make possessor the possessor of box, for the write that needs them.

The box points at the possessor’s one possession state, as the middleware’s handover points it. The state is found by a query, as the middleware finds it, never from its IRI. A possessor that has a state keeps it, and its link is not written again. A possessor without one gets <possessor>_possession, the IRI the middleware gives a state it creates, typed cfc:PossessionState and linked from the possessor, so the state comes into being with its first box.

Raises:

ValueError – If possessor has more than one possession state, as the middleware raises: a resource has one.

jms_kapps.uc2.seed.place_box(ogm: OGM, box: IRI, *, on: IRI, origin: IRI, destination: IRI, transport: IRI | None = None) → IRI[source]#

Create box in the possession of module on, with its transport running from origin to destination and assigned to on, and return the transport.

The seed chooses the transport’s IRI: transport if given, and otherwise the one the WarehouseManagementSystem’s opening gives a transport. The box links to its transport (fc:hasTransport) and the transport to its box (fc:hasBox), both written, as the opening writes them. The box points at the module’s one possession state (see possession_triples). The transport names no capability: a module’s BoxTransportCapability comes into the graph when the module registers its BoxTransportWorkflow, after the seed.

The box, its possession and its transport arrive in one write, because each needs the others: a box on a module must have a transport, and the box of a running transport must be on exactly one module. A seed is demonstration setup, made before any participant starts, so it writes directly and not through a context manager of the middleware.

Raises:

ValueError – If the box or its transport is in the graph already, or the module has more than one possession state.
