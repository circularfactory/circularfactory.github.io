jms_kapps.evaluation.replay#

The replay of the store-only baseline: the store requests of a recorded UC2 run, sent again straight to the store, with nothing of KSM, the object-graph mapper or the triple-store interface on the way. This module imports none of them; the baseline (baseline) prepares the store and reads the answers.

Its own login. The replay logs in with its own credentials, from TRIPLESTORE_URL, TRIPLESTORE_USERNAME and TRIPLESTORE_PASSWORD, each with its GRAPHDB_* variable as the deprecated fallback, as the triple-store interface reads them (store_login). A recorded login carries no secret, so the replay sends none again.

Its own repository. Each request goes to the baseline’s own repository in place of the one the recording names, whatever that is (retargeted), through part 1’s name guard (store.guarded): eval- and a run id, never jms-kapps, kapps-demo or Tests.

Before the window, the requests go out in their order, each after the answer to the one before (Replay.send_in_order). In the window, each goes out at its recorded offset from the window’s start, by the clock, and the replay never waits for an answer before it sends the next: requests whose offsets overlap go out at the same time, each on a thread of its own (Replay.send_at_offsets). Of each request it keeps when it left, how late that was against its offset, how long the store took to answer it, and the store’s status, media type and size of its answer; the answer itself only where it is no success, or where the caller asks for it. A request that got no answer within REQUEST_TIMEOUT_SECONDS, or whose connection dropped, has the error instead. A request that the replay could not send at all, a fault of its own and no answer of the store, ends the window with that fault (ReplayedWindow.answers).

send_at_offsets(requests: Sequence[Request], seconds: float) → ReplayedWindow[source]#

Start the window now, send each of requests at its offset from the window’s start, without waiting for an answer, and return at the window’s end, seconds after its start. The requests still open then are answered in ReplayedWindow.answers.

A request leaves on a thread of its own, and the next is sent only once it has left, so that its time of leaving is its own; a request that left late keeps by how much.
