jms_kapps.uc2.process#

One FlexConveyorModule as its own process, behind its own middleware instance.

The process registers the module’s service and its three workflows in the graph, Reserve, Receive and the BoxTransportWorkflow, serves them over REST, takes every notification through the middleware, and answers one command outside the workflows: arming and disarming each of its two faults, POST /faults/{name}. It serves its handover event stream, and commits where it lives at startup. Its activity feed is on, and so is the middleware’s state dashboard: the library’s own boxes, and a tab named after the module with three of its own, which draw the module from above and show its routing decisions and the connections it read (module_dashboard). Uvicorn runs on the main thread, so that a signal reaches it and the middleware deregisters on the way out. From the stop signal on, the module waits, the graceful-shutdown bound at most, for the box it reserved itself for and for its own work, and ends the transport that is its to end; the shutdown waits for that (added on 2026-10-06, jms_kapps 42, decided by Etienne).

Changed on 2026-10-05, at Etienne Hoffmann’s request after his hands-on test of use case 2 (the ticket “Each UC2 module’s dashboard shows the module, its routing decisions and the adjacency matrix it read (424)” in kapps_semantic_middleware). Until then the dashboard had the library’s boxes only, and the paragraph above read: “Its activity feed is on, and so is the middleware’s state dashboard, with the library’s own boxes only.”

The move of a box off the module, its convey, is simulated: it waits the module’s own transit time, which the module reads from the graph once, when it starts (fc:hasTransitTime, written by the launch’s seed), and not at all where that is 0. A module whose graph holds none, or more than one, does not start: its process ends with the reason. (Changed on 2026-10-07, jms_kapps 8, decided by Etienne. Until then: “it waits the transit time, which is set per run”, given on the command line.) A real FlexConveyor passes a move that drives its motor, and nothing else changes. Convey is no workflow of a module: no peer calls it. (Changed on 2026-10-06, jms_kapps 40, decided by Etienne. Until then the module registered four workflows, Convey among them, which the receiving module of a hop called.)

Run it as python -m jms_kapps.uc2.process –resource-iri <module IRI>, the command line module_command builds. The Launcher does.

The WarehouseManagementSystem and the monitor run the same way, each behind a middleware instance of its own. The three share the command line and the start of common.process, process_parser and run_process, and the WarehouseManagementSystem also takes the module’s call of a peer and its notification helper. (Changed on 2026-10-06, jms_kapps 41: the WarehouseManagementSystem moves no box, decided by Etienne. Until then it took “the module’s transit time and notification helpers”.)

jms_kapps.uc2.process.mount_fault_switches(app: FastAPI, module: FlexConveyorModule) → None[source]#

Serve module’s fault switches on app: POST /faults/{name} with {“armed”: …}.

Not a workflow: a fault is an operator’s switch on this process, not a capability of the module, so the graph names none. A restart builds a new module, with every fault off. The route is left out of the module’s API docs, which the Launcher page links: the Launcher is the writer of the switches, and holds what it commanded, so a person switches a fault there.

jms_kapps.uc2.process.build(resource_iri: str, ogm: ~kapps_ogm.ogm.OGM, host: str, port: int, *, retry_seconds: float = 1.0, move: ~collections.abc.Callable[[~kapps_triplestore_interface.utils.iri.IRI, ~kapps_triplestore_interface.utils.iri.IRI], None] | None = None, strategy: ~jms_kapps.uc2.strategies.ModuleStrategy = <jms_kapps.uc2.strategies.RealModuleStrategy object>, strategy_name: str = 'real', deadlock_alarm_seconds: float = 300.0) → SemanticMiddleware[source]#

The middleware instance for one module, with its three workflows, its notification handler, the fault command, its handover event stream and its state dashboard.

The module’s transit time, how long the simulated move of a box takes, is read from the graph once, here, with the longest one of any module, T: a box the module reserved itself for may take ARRIVAL_BOUND_SECONDS and T to arrive, or ARRIVAL_BOUND_SECONDS and two T for a box reserved ahead, at a look-ahead.

Parameters:

  • retry_seconds – How long the module waits before it asks again the Reserve of a module that refused to reserve itself, once its detour has refused too (changed on 2026-10-06, jms_kapps 43: until then “an occupied or reserved module’s Reserve”).

  • move – The move of a box off the module, in place of the simulated one.

  • strategy – The module strategy, which names the neighbours the module asks for a box.

  • strategy_name – Its name, –module-strategy.

  • deadlock_alarm_seconds – How long a box the module holds may wait for a Reserve before the module raises the deadlock alarm for it, –deadlock-alarm-seconds (added on 2026-10-11, jms_kapps 77, decided by Etienne).

Raises:

TransitTimeError – If the graph holds no transit time for the module, or more than one. Nothing is registered then.
