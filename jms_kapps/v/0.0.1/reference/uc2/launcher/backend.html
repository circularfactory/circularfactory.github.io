jms_kapps.uc2.launcher.backend#

What the Launcher does, without a route or a page: launch a topology, stop processes, arm faults.

The Launcher runs on the run core (run_core), which the bench launcher shares. A launch stops whatever runs, asks the one live-instance guard, clears the dataset, seeds the topology, and starts the participants of every run, one FlexConveyorModule process for each module and the WarehouseManagementSystem’s, through a fresh Supervisor, and beside them the monitor. The monitor is the Launcher’s own: a run of the run core without the Launcher starts none, so its resource is reserved here (launchable), and the Launcher’s graph seeds it. api.py serves this over HTTP, and static/ is the page that calls it.

A launch names the strategy of the modules and the strategy of the WarehouseManagementSystem, or runs with the Launcher’s own, jms-uc2 –module-strategy and –wms-strategy, real unless they name others (strategies). The Launcher finds the strategies of each kind once, when it is made, and refuses a launch that names one it did not find before it stops anything. The run core puts –module-strategy <name> on the command line of every module process and –wms-strategy <name> on the WarehouseManagementSystem’s (run_core.participants_of), and each process loads its strategy by that name at its start. (Added on 2026-10-10, jms_kapps 52, decided by Etienne on 2026-10-07.)

A launch says whether it collects history, the launch option collect_history, or runs with the Launcher’s own, jms-uc2 –collect-history, off unless it is given. A launch with it has its reset turn on the store’s history collection, so that past possessions can be read; one without it leaves the collection as it is, on where an earlier launch turned it on. The state says whether the launch that runs was launched with it. (Added on 2026-10-10, jms_kapps 22, with the names Etienne decided on 2026-10-07.)

A launch names the deadlock alarm time of its modules, or runs with the Launcher’s own, jms-uc2 –deadlock-alarm-seconds, 300 s unless it is given: how long a box a module holds may wait for a Reserve before the module raises the deadlock alarm for it. The run core puts –deadlock-alarm-seconds <seconds> on the command line of every module process. The page’s field “deadlock alarm (s)” starts at the Launcher’s own; the API refuses a value that is not a positive number, before anything is stopped or cleared. (Added on 2026-10-11, jms_kapps 77, decided by Etienne.)

Clear stops every process, then empties the dataset, graph by graph, and says how many statements the dataset holds then: 0 where it is empty. It asks the one live-instance guard as a launch does, after this Launcher’s processes have stopped, so it clears nothing while another launcher’s process, or a process run on its own, is live there. A clear of the whole dataset in one request is refused while the store collects history, so each graph is cleared on its own (triplestore.clear_graph_by_graph). From the clear on, no topology shows as seeded, and the next launch loads the ontologies, the shapes and a topology again. (Added on 2026-10-10, jms_kapps 5, decided by Etienne on 2026-10-05, who asked for a clear button that kills every process and clears the whole of the store’s unit, the dataset.)

Each refusal of the Launcher has a class of its own: its own, NoProcess and NotReachable; the load check’s, TopologyRefused (launchable); and those it passes on from the run core and the strategies, LiveInstanceError, LaunchFailed, ClearFailed and UnknownStrategy. Its routes catch only refusals, so any other error, as a bug’s, goes through them as it is (api.py). (Added on 2026-10-11, jms_kapps 33.)

The graph and the modules’ fault switches are reached through two small ports, LauncherGraph, the run core’s RunGraph with the clear beside it, and FaultSwitches, so that a test can replace both. (Changed on 2026-10-10, jms_kapps 5: until then the graph’s port was “the run core’s RunGraph”.)

The Launcher holds each module’s two faults. It writes each switch, and it supervises the processes that reset a module to off, so it knows what it set and when the value is gone. The page therefore shows what the Launcher commanded, and no read of the page reaches out to a module. A switch goes to the address the supervisor read when the module turned live, not to one read from the graph now: a module run by hand on the same resource can win the graph’s answer, and the switch then works while the graph is away. A write through a module’s own POST /faults/{name} is not seen here.

Nor does a read of the page reach the graph. The supervisor reads the services in its own watch, each with the address it keeps from the read that found its process live. state() renders what the supervisor last read. While the graph cannot be read, a state that rests on it is shown as unconfirmed, with how long ago it was last confirmed, and the page keeps answering. The list of the boxes on the station is read the same way, in the background, by its one SPARQL query (boxes.StationBoxes), and state() renders the last read with the query’s text. (The last sentence added on 2026-10-10, jms_kapps 23, decided by Etienne on 2026-10-05.)

One process, as the page shows it: the supervisor’s snapshot of it, child, and what the page needs besides.

The page reads one object for each process, the snapshot’s fields beside the page’s own, as it did before the snapshot was composed here: so the snapshot’s fields are written out flat, and read back from flat, as FastAPI reads back every answer it sends. A snapshot’s stoppable is whether the page may offer a stop: the process still runs, and no stop has reached it. Bases: object

The processes of one use case 2 runtime, and the topology they were launched from.

One launch, stop-all or clear runs at a time. The page’s reads and single commands do not wait for one: they act on whichever supervisor and topology are current when they start.

The armed faults are held here rather than read back from the modules, because this object is the only thing that arms one. A launch starts fresh processes and a stop ends one, and both forget what they were told.

  • wms_command – The command line of the WarehouseManagementSystem’s process.

  • monitor_command – The command line of the monitor’s process.

  • transit_seconds – The transit time of a launch that names none: the default of the page’s field, jms-uc2 –transit-time.

  • faults – The modules’ fault switches.

  • echo – Where command lines and the children’s output go. The Launcher’s stdout if None.

  • stop_timeout – How long a stop waits before it kills a process.

  • module_strategies – The module strategies a launch may name, by name: those registered in their entry-point group if None (strategies.found).

  • wms_strategies – The WMS strategies a launch may name, by name: likewise.

  • module_strategy – The module strategy of a launch that names none: jms-uc2 –module-strategy.

  • wms_strategy – The WMS strategy of a launch that names none: jms-uc2 –wms-strategy.

launch(topology: Topology, *, name: str | None = None, force: bool = False, transit_seconds: float | None = None, module_strategy: str | None = None, wms_strategy: str | None = None, collect_history: bool | None = None, deadlock_alarm_seconds: float | None = None) → None[source]#

Stop what runs, clear the dataset, seed topology, and start its processes: the run core’s participants of topology, and the monitor.

A clear cannot be undone, so it clears only while no other process’s service is live there: the run core’s live-instance guard asks the graph after this Launcher’s own processes have stopped. A process that stops when asked deregisters its service first. One that was killed, or that had exited on its own, may have left its service live until its last heartbeat is MAX_HEARTBEAT_AGE_SECONDS old. That is this Launcher’s own dead process, and the seed clears what it left, so the guard leaves it out. Any other live service refuses the launch: another launcher’s, or that of a module run on its own from its printed command line, even on a resource this Launcher stopped cleanly.

Parameters:

  • topology – The modules to seed and start.

  • name – What to call it on the page. The shipped topology’s name, a path, or what the page calls a topology edited on it.

  • force – Clear the dataset even while another process’s service there is live.

  • transit_seconds – The transit time of every module that has none of its own in topology. The Launcher’s default if None. 0 is allowed.

  • module_strategy – The name of the module strategy every module process runs with, –module-strategy on its command line. The Launcher’s default if None.

  • wms_strategy – The name of the WMS strategy the WarehouseManagementSystem’s process runs with, –wms-strategy on its command line. The Launcher’s default if None.

  • collect_history – Whether the reset turns on the store’s history collection, after it loaded the ontology; without it, the collection stays as it is. The Launcher’s default if None.

  • deadlock_alarm_seconds – How long a box a module holds may wait for a Reserve before the module raises the deadlock alarm for it, –deadlock-alarm-seconds on every module’s command line: a positive number of seconds. The Launcher’s default if None.

Raises:

  • TopologyRefused – If a module of topology takes the monitor’s resource (launchable). Nothing is stopped or cleared then.

  • UnknownStrategy – If this Launcher found no strategy of its kind by module_strategy or wms_strategy, naming it and the strategies of its kind. Nothing is stopped or cleared then.

  • LiveInstanceError – If another process’s service is live and force is false, naming each live resource. Nothing is cleared then, and this Launcher’s processes stay stopped.

  • LaunchFailed – If the graph cannot say which services are live, or seeding or starting a process failed, naming why. Nothing runs then.

clear() → Cleared[source]#

Stop every process, then clear every graph of the dataset, one by one, and say how many statements it holds then.

The stop and the guard are a launch’s: this Launcher’s processes stop first and deregister as they go, and the clear goes on only while no other process’s service is live in the dataset. A clear cannot be undone, and the page has no way to force one. From the clear on, no topology shows as seeded, nor the strategies and the history option it was launched with, unless the store refused before it cleared any graph; the processes stay on the page, stopped. The next launch seeds the ontologies, the shapes and its topology again. (Added on 2026-10-10, jms_kapps 5.)

Raises:

  • LiveInstanceError – If another process’s service is live, naming each live resource. Nothing is cleared then, and this Launcher’s processes stay stopped.

  • ClearFailed – If the graph cannot say which services are live, and nothing is cleared; or if the store did not list or clear a graph, or did not say how many statements are left, naming why.

The strategies a launch may name, of each kind, as this Launcher found them. Like state(), it calls neither a process nor the graph.

process(id: str) → ChildSnapshot | None[source]#

The process whose id in the Launcher’s paths is id (see process_id), as the supervisor holds it now, or None where no process of the current launch has that id. Like state(), it calls neither a process nor the graph. (Changed on 2026-10-11, jms_kapps 33: until then it raised a KeyError where none had the id.)

state() → LauncherState[source]#

Everything the page shows.

It renders what this process already holds, and calls neither a module nor the graph, so a poll answers at once whatever else is away. The addresses are the supervisor’s, kept for live processes only: a killed one can leave its address behind.
