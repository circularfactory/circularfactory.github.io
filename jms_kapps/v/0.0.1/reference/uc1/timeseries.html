jms_kapps.uc1.timeseries#

The time-series store of use case 1: InfluxDB 3, through its HTTP API.

The raw curves of an unscrewing attempt are too many and too fast for the knowledge graph. So the graph holds the attempt’s operation and one reference to its frame, and the curves are here. The screwing resource writes each frame with a FrameWriter, and stores the reference that the writer gives back on the operation. The detector and the learner read a frame back with a FrameReader, from the reference that they find on an operation.

The layout. Each frame is in one table, unscrewing, as one row for each sample:

  • time: the sample time.

  • One float column for each signal: robot_position, axial_force, unscrewing_torque. A signal that a later frame adds becomes a new column. The earlier frames have no value in it.

  • The tag frame: an id that the writer gives the frame. It selects the frame’s rows.

  • The tag phase: the sample’s phase. A sample without a known phase has no phase tag, because InfluxDB has no empty tag value. So a frame recorded without phases has the same layout as one recorded with them, and a query by phase does not find it. One frame can hold both kinds of sample: a legacy mock frame has no phase after the disassembly.

  • The tag source: only on a replayed frame, and it names the recording.

The writer creates the database and the table with these tags, in this order, before its first write. So the first frame that a store gets does not decide the layout.

The reference is a URI relative to the store that the reader is connected to: influxdb:///<database>/<table>?frame=<id>&start=<time>&stop=<time>. It names no server, as the graph names no triple store. The times are the frame’s first and last sample, in RFC 3339 with nanoseconds. The reader reads only between them, so a read touches the store’s files for those seconds only, however long the history is.

The connection comes from the environment: the server that INFLUXDB_URL names, with INFLUXDB_TOKEN if the server asks for a token. Only without INFLUXDB_URL does the client connect to the local service that compose.yaml starts, which asks for no token: the local stack is only the fallback. The database is never read from the environment. The caller names it, and it defaults to jms-kapps, the name of the dataset of these use cases.

Changed on 2026-10-05, after Etienne Hoffmann decided that every demo runs on the configured store and that the local one is only the fallback; the ticket of that decision, on jms_kapps’ demos on the configured live store (kapps_semantic_middleware 422), asks that no text call the local stack the default. Which server the client connects to did not change. Until then the paragraph began: “The connection comes from the environment. INFLUXDB_URL defaults to the local service that compose.yaml starts, which asks for no token. A shared server is the opt-in: set INFLUXDB_URL, and INFLUXDB_TOKEN if the server asks for a token.”

class jms_kapps.uc1.timeseries.FrameReader(influxdb: InfluxDB)[source]#

Bases: object

Reads frames back through their references, for the detector and the learner.

One read is one attempt. A reference names one frame and its time window, which is one unscrewing attempt, and the reader reads only within that window. The learner reads each new operation’s curves through that operation’s own reference, never all of history in one query, so no query spans more than one attempt. InfluxDB 3 Core limits how many files one query may read, about 72 hours of data by default; a read of one attempt stays far below it.

read(reference: FrameReference | str) → Frame[source]#

The frame that reference names, as it was written.

Raises:

  • FrameNotFound – If the store holds no row of that frame.

  • InfluxDBError – If the store refuses the query, for example for a table it lacks.

  • ValueError – If the rows do not make one frame.
