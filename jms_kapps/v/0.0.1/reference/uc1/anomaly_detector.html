jms_kapps.uc1.anomaly_detector#

The anomaly detector of use case 1: it classifies one recorded unscrewing attempt, and ends its operation.

It is called, not notified. After each attempt, the screwing resource calls the detector’s classify workflow with the IRI of the unscrewing operation (classify_call.ClassifyRequest), which is running and holds its time-series reference. The screwing resource finds the workflow in the graph by the detector’s :ClassifyCapability, and reads nothing of the answer: the detector ends the operation.

One classification is one commit of the middleware, mw.commit():

  • Body: the effective values of the operation’s Screw (effective_values), read afresh for every attempt, so a value that the learner changed counts from the next attempt; the frame that the operation’s time-series reference names (timeseries.FrameReader); and the decision tree (decision_tree.classify). Then the classification as a prov:Activity, with the detector’s resource as its agent (prov:wasAssociatedWith) and its end time (prov:endedAtTime), and the decision snapshot, a new instance of the ten values that names that activity (prov:wasGeneratedBy), each with mw.create(), which joins the commit; and through transition.update(…) the operation’s outcome, its link to the snapshot, and after a failure outcome the measured end position of its approach.

  • Clean exit: all of that and the operation’s done, as one write.

  • Error in the body: nothing of the body is written, and the operation is committed failed, with why as its svc:executionResult (it begins with NOT_CLASSIFIED): a Screw without its placement values, a frame that the store lacks or that cannot be read, or curves that the tree refuses.

It ends an operation only while the operation is `running`. From running on, the screwing resource that took the operation is responsible for it. It may end the operation failed itself, when the detector does not answer in time. An operation that is not running when the call comes is left as it is: nothing else is read, and nothing is written. When the detector ends an operation, at the clean exit or on an error, it reads the status again. An operation that is no longer running is left as it is too, and nothing of the classification is written. Each time, the detector logs one line, left_as_it_is_record.

The store’s check closes part of the gap between that read and the write: the write removes the status that the object-graph mapper read just before it, and the store refuses the write when that status is gone (PreconditionFailedError). The detector then reads the operation again, and leaves it as it is when it has ended. The mapper reads the status at the write itself, though, so a status that changed between the detector’s read and the mapper’s read is still overwritten. The libraries give a write no precondition on a value that the writer read earlier.

The detector sends no notification of its own. The planner, which issued the operation, learns of the end from the middleware: after the store admits the commit that ends the operation done or failed, mw.commit() notifies the operation’s issuer (svc:issuedBy), in the background. A commit that writes nothing, because the operation ended meanwhile, notifies nobody.

The answer of the classify workflow, ClassifyAnswer, says what the call did with the operation, for a person who calls the workflow. The detector refuses a call, with an error, in two cases only: it cannot read the operation, or its failed did not reach the store and the operation is still running. Then the screwing resource ends the operation failed itself.

Its activity feed is on, and so is the middleware’s state dashboard, with the library’s own boxes only, as for every party of use case 2.

Run it as python -m jms_kapps.uc1.anomaly_detector –dataset <name>. It starts and serves as every participant’s process does, through common.process, with the local InfluxDB unless INFLUXDB_URL names another. jms-uc1 starts it (run_core).
