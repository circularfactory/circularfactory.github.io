jms-kapps#

The two use cases of the paper KAPPS: A knowledge-based CPPS Architecture for the Circular Factory (arXiv 2605.22457), built on kapps-semantic-middleware.

In KAPPS, the parts of a cyber-physical production system do not call each other by fixed addresses. Each part is a participant: a program with its own instance of the semantic middleware. Participants find each other in a knowledge graph, and every change they make to the factory’s state is a write to that graph, which the triple store checks against SHACL shapes, rules it validates at every commit, before it admits the write.

  • Use case 2 — the decentral FlexConveyor. Each conveyor module runs as its own process. A module reserves the next module for a box, conveys the box, and hands it over. No central router exists: each module chooses the next module from the graph. Two faults that a person arms on a module show the store refusing a write the module should not have made.

  • Use case 1 — vertical integration. Four participants work an unscrewing operation. A planner opens one operation per press. A screwing resource records the attempt’s curves. An anomaly detector classifies the attempt. A learner refines the detection thresholds of each Screw type. They coordinate through the knowledge graph and find each other there. The notifications and the call of the detector go over REST, to addresses that the graph names; the curves go through InfluxDB.

Both use cases are in one repository, because they share the ontology bootstrap, the triple store setup and the measurement harness, and because the paper cites them together.

Run use case 2#

On Linux or macOS, with Docker and uv, the clone first, then in the repository root:

git clone https://github.com/circularfactory/jms_kapps.git && cd jms_kapps
docker compose up -d --wait   # a local triple store, with the dataset jms-kapps, and an InfluxDB
uv sync --locked              # the packages, into .venv
export TRIPLESTORE_URL=http://localhost:7200 TRIPLESTORE_USERNAME=admin TRIPLESTORE_PASSWORD=root
./run-uc2

./run-uc2 starts use case 2 and opens the Launcher page on http://127.0.0.1:8090/. It runs on the triple store that TRIPLESTORE_URL names; without that variable, it starts the local store itself first. It clears the dataset it runs on: jms-kapps, unless --dataset names another. A dataset is the store’s unit, one set of graphs. Every argument goes on to jms-uc2, as in ./run-uc2 --topology merge-fault-demo. Ctrl+C stops every process of the run.

uv sync needs no account: uv.lock takes the three sibling packages from PyPI. jms_kapps itself is not on PyPI; you run it from a clone.

The reviewer guide is the one path from a clean machine to a running use case 2: what to install, the setup, what each page shows, how to use the two faults, how to stop, and how to run the tests.

What you see#

The Launcher page starts one process for each module of a topology, the modules of a station and their connections, plus the WarehouseManagementSystem (WMS), which spawns boxes and takes them back, and a monitor, which only reads the graph. It lists each process with its state, links to each one’s dashboard, arms each module’s two faults, and launches another topology.

Open the WMS and spawn a box. The box travels from module to module to its destination. Each step of its journey is a hop: the giving module asks the next module to reserve itself, commits the handover, the change of the box’s possessor, and moves the box. The store admits or refuses each commit before anything moves. The monitor draws the station from the graph alone, and shows each write the store refused, with the shape that refused it.

The paper’s words and the demo’s#

The paper says

The demo shows

service

a participant’s process, with its own middleware instance

operation

a box’s transport, in use case 2; an unscrewing operation, in use case 1

fault injection

the two faults a person arms on a module: skip-reserve and complete-without-releasing

the OGM

the object-graph mapper, which turns the middleware’s Python objects into triples and back

the knowledge graph

the graph: the dataset of the triple store that a run uses

The glossary defines every other word these pages keep: dataset, participant, hop, handover, heartbeat, deregister, stale, IRI, SSE and more.

Run use case 1#

With the same setup as use case 2:

uv run jms-uc1

jms-uc1 seeds the demo’s two angle grinders, starts the four participants of use case 1, and prints the address of each one’s dashboard. It clears the dataset it runs on: jms-kapps, unless --dataset names another, and it refuses while another service is live there, unless --force. Its page, on http://127.0.0.1:8091/, shows each participant and links to its dashboard. Press Unscrew on the planner’s dashboard to open one unscrewing operation. Ctrl+C stops all four. jms-uc1 seed seeds once and prints each participant’s command line instead, to run them by hand. See Use case 1.

On Windows#

./run-uc2 is a bash script, so the one command needs Linux, macOS or WSL. On Windows itself, take the long way: start the local store with docker compose up -d --wait, set the three variables as The triple store shows for PowerShell or cmd.exe, and run uv run jms-uc2. Every process prints its command line in the form of the platform’s shell, so each also runs on its own there.

Requirements#

  • Python 3.12 or later. uv installs it where the machine has none.

  • uv. Do not use Poetry, and do not install into a global Python.

  • A triple store with a dataset that validates SHACL shapes. Where none is configured, docker compose up -d --wait brings a local one up, dataset included: see The triple store.

  • For use case 1, an InfluxDB 3. The same command brings a local one up: see Use case 1.

  • Three sibling packages from PyPI, pinned in pyproject.toml and locked in uv.lock:

    • kapps-semantic-middleware 0.2.1

    • kapps-triplestore-interface 2.2.1

    • kapps-ogm 0.3.1

Script

Runs

jms-uc2

Use case 2 from a topology, behind the Launcher page. Clears the dataset it runs against, --dataset. See The Launcher.

Use case 2’s vertical slice: two modules, a clean handover and a refused one, then exit. Clears the dataset it runs against. See The vertical slice.

jms-eval

One command from a spec of the harness to its report and table.

jms-eval-sweep

The runs of a spec, one by one, skipping a run whose record exists.

jms-eval-table

The numbers of the runs of a spec, as one table beside their records.

jms-eval-report

Layout#

jms_kapps/
├── compose.yaml    the local fallback: a triple store, with the dataset created, and an InfluxDB
├── run-uc2         the one command of use case 2
├── docs/           the reviewer guide, its screenshots, and the reference pages
├── graphdb/        the dataset's configuration
├── scripts/        the release's checks of this tree, which its hygiene workflow runs
├── tests/
└── src/jms_kapps/
    ├── common/     what both use cases use: the ontology bootstrap, the store setup, the process supervision
    ├── uc1/        use case 1, with its ontology and its recordings
    ├── uc2/        use case 2, with its ontology, its shapes, its topologies and its pages
    └── evaluation/ the measurement harness, which the use cases import nothing from

Each asset is below the package that uses it, so the wheel carries it, and an installed copy reads it with importlib.resources.

Development#

uv sync --locked
uv run pytest -m "not live"          # the offline tier: no triple store, no InfluxDB
uv run ruff check && uv run mypy
uv run pytest --dataset <name>       # with the store's variables set: also the tests that clear <name>

A test marked graphdb clears the dataset it runs against, so name a throwaway one, never the demo’s. See Tests.

Acknowledgements#

The Python of the artifact is not carried forward: it was written against frozen libraries, so both use cases are written again from the start. See The assets.
