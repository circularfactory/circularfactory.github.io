jms_kapps.uc2.launcher.api#

The Launcher’s HTTP surface: JSON routes over backend.Launcher, and the static page.

The backend answers in JSON only, and renders no HTML. The page in static/ is plain HTML, JavaScript and CSS, and learns everything it shows from these routes. The pattern is the middleware’s transferunits demo, index.py plus templates/index.html, with the two halves kept apart.

A launch names a shipped topology, or carries one edited on the page, which the server checks itself. Launching clears the dataset and seeds it again. A shipped topology is chosen by its name. An edited one comes whole, as the body of the request: a module list, the one topology format, which the shipped topologies have too (see topology.py); the server runs the load check on it again and launches it only if it passes, because the page’s own result is never taken as the check. /api/topology/check runs the same check alone, so the page can show its reason while a person edits. Anything but a module list, such as the short topology document this package had before, fails the check with a reason that names the format. Either launch meets the same guards, and the page has no way to force one. A topology file of one’s own opens in the page’s editor, which launches it as an edited topology, or goes in at the command line, jms-uc2 –topology <path>, where the person starting the run supplies it.

The page’s editor reads and writes a topology through these routes. It starts from a shipped topology, which GET /api/topologies/<name> gives as its module list, from an empty grid, or from a topology file a person uploads, whose bytes POST /api/topology/file reads as the command line reads a file, and lays out as POST /api/topology/layout lays out a module list. The page saves what the editor holds as a topology file itself: a module list it writes, as below. POST /api/topology/layout gives the modules of a module list and a cell on a grid for each, by the one layout rule, Topology.places; GET /api/topology/format gives the namespaces and keys a module list is written with, those of topology.py; and the load check above decides what may launch. So the page carries no reader of the format, no layout rule and no load check of its own. Once a topology is open, the editor keeps each module on its cell, and puts a module it adds on the cell clicked: laying out again on each change would move a module that is not connected yet to a row below, away from where a person put it. A launch of an edited topology names the topology its editor started from, and the page calls the running topology by it: cross (edited) (edited_name).

A route answers with an error only for a refusal of the backend’s own, each of a class of its own: a process or a module that a command names and that does not run (NoProcess), a module that does not take a fault switch (NotReachable), a topology that loading refuses (TopologyRefused) or a name that the package ships no topology by (UnknownTopology), a strategy that the Launcher did not find (UnknownStrategy), and a launch or a clear that the live-instance guard refuses (LiveInstanceError) or that fails (LaunchFailed, ClearFailed). Any other error goes through the route as it is, and the server answers it as the fault it is: a bug’s KeyError or ValueError is not taken for a refusal that names a wrong cause.

jms_kapps.uc2.launcher.api.create_app(launcher: Launcher) → FastAPI[source]#

The Launcher’s app.

A route that blocks is a plain function, so FastAPI runs it off the event loop. Every page of every process is under /p/<id>/, through the Launcher’s own port: see passthrough. While the app serves, the Launcher reads the boxes on the station in the background (boxes.StationBoxes), whether a page is open or not, so that GET /api/state answers them from memory.
