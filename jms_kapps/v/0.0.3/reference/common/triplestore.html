jms_kapps.common.triplestore#

The triple store both use cases run against, and how an ontology or a shapes file gets into it.

Every store is built by the triple-store interface’s connect(), through the middleware’s triplestore_for, and is typed by the interface’s contract, TripleStore. The store’s URL and the identity come from the environment, exactly as the middleware’s own examples read them: TRIPLESTORE_URL, TRIPLESTORE_USERNAME and TRIPLESTORE_PASSWORD. The dataset never does. A seed clears the dataset it is pointed at, so the caller always names it, and the name defaults to the one dataset these use cases own. Every demo runs on the configured store. On it, create that dataset once from graphdb/jms-kapps-repo-config.ttl. The local store that the project’s compose.yaml brings up, only the fallback for a machine on which no store is configured, has it already.

The store is built by connect() and named in the interface’s terms, the dataset and the TRIPLESTORE_* variables; the reset sets the shapes with the store’s shapes_set.

The reset seeds a demonstration or test dataset: a productive store already holds the ontologies and shapes, and no service calls the reset (services use this module only to connect and to read).

A dataset is emptied whole by clear_graph_by_graph, the Launcher’s Clear: every graph, one by one, and then the count of the statements it still holds.

jms_kapps.common.triplestore.reset(store: TripleStore, *, ontology: str, shapes: str | None, individuals: str = '') → None[source]#

Empty the dataset, load one use case’s ontology and shapes into it, then a seed’s individuals, and register jms_kapps’ prefixes in it.

The order matters. The old data goes first, because a store validates the data it already holds against its shapes the moment the shapes change. Then the shapes, which replace every shape the dataset had, through the store’s shapes_set; a dataset without SHACL validation refuses them. The middleware’s operation-status shape joins every shapes document the reset sends, an empty one too (with_operation_status_shape): the demonstrations seed it, the same way they load the middleware’s service ontology, and a productive knowledge graph already holds it. With shapes None, the reset sends no shapes at all, for a dataset without SHACL validation that a caller seeds on purpose, as the measurement harness seeds its SHACL-off twin. Then Core, svc: and mes:, then the use case’s ontology into the default graph, which is where the middleware looks for its alignment axioms, then the individuals, also as Turtle, into the default graph. The prefixes come last, after every import, because an import adds back the names nobody chose that register_prefixes deletes.

Core, svc: and mes: each live in a named graph of their own, which the clear leaves standing, and each seed loads them again from the installed middleware. A dataset seeded under an earlier release of the middleware would otherwise keep that release’s svc:, and the object-graph mapper refuses a write of a term that a newer release added, such as the issuer that the middleware’s issue_operation() writes.

Raises:

TripleStoreNotSupportedError – If the dataset has no SHACL validation and shapes is not None, so that the shapes would validate nothing. Only the old data is cleared then.

exception jms_kapps.common.triplestore.ClearFailed(message: str, *, nothing_cleared: bool = False)[source]#

Bases: RuntimeError

A clear of a dataset stopped part-way: the store did not clear one of its graphs or its shapes, did not list its graphs, or did not say how many statements are left. The message says which and why, for a person to read. nothing_cleared is whether it stopped before any graph was cleared, so that the dataset holds what it held.

jms_kapps.common.triplestore.clear_graph_by_graph(store: TripleStore) → int[source]#

Clear every graph of the dataset, one by one, and its shapes, and return how many statements it holds then: 0 where it is empty.

The store lists its named graphs first, by a standard SPARQL query, so that a store that cannot list them has nothing cleared. Then the default graph is cleared, then the named graphs of the shared ontologies, each whether it holds anything or not, then the shapes, through the store’s shapes_set with an empty document; then every other named graph the store listed, such as one a person loaded or another program wrote, or the one in which the middleware keeps the receipts of writes that a stopped process left, urn:x-kapps:write-receipts. That is the order in which a reset clears the first three (reset), which a store that validates with shapes takes: the data goes before the ontologies and the shapes it is checked against. A dataset without SHACL validation has no shapes to remove, and its store refuses shapes_set as not supported: the clear goes on. One request for each graph, through the interface’s and the middleware’s own calls, and never one request for the whole dataset: the store refuses that while it collects history, and clears each graph (measured on the KIT store on 2026-10-01). Nothing here turns the history collection off: a clear while it is off is not recorded, and the cleared data would then disappear from every earlier point in time.

The interface takes every absolute IRI as the name of a graph, so the receipts graph is listed and cleared as any other.

The count is statement_count, of the statements written, after the last clear.

Raises:

ClearFailed – If the store did not list its named graphs, and nothing was cleared. If it did not clear a graph or the shapes, naming which, the dataset and why; nothing later is cleared then. Or if it did not say how many statements are left.

jms_kapps.common.triplestore.statement_count(db: Queryable) → int[source]#

How many statements the dataset holds as written: in its default graph and in every named graph, leaving out what its reasoner infers, since a dataset that holds none still infers the axioms of its ruleset.

The scope of the written statements is stated through the interface’s query builder (include_implicit=False), which writes it in the form its store understands. On the KIT store that scope is the written statements of the default graph alone, beside every named graph of the dataset (the documentation of its query behaviour), so each named graph is counted on its own. A statement of the default scope that a named graph holds too is counted there only, so the count is the same where a store’s default scope takes in its named graphs, and a statement that the default graph and a named graph both hold is counted once.
