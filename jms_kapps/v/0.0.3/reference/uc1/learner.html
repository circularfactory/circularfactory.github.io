jms_kapps.uc1.learner#

The learner of use case 1: it refines a threshold of each Screw type from the graph’s history.

The learner is a participant of its own, with its own resource and its own middleware instance (learner_process). No notification starts it: it runs every so often, as the KAPPS paper’s learner “periodically queries” the graph. Each run:

  1. finds, in one query, the unscrewing operations that are done with the outcome ScrewIntact and that it has not learned from yet, each with its Screw type and its time-series reference;

  2. reads the curves of each through that operation’s own reference, one attempt per read, so no read spans more than one attempt;

  3. derives the maximum dynamic torque of each Screw type with the placeholder rule below;

  4. commits each value that changed to its Screw type, all of them in one mw.commit(). It never writes to a Screw, and never a placement value: a Screw holds no type value, and a placement value depends on where the screw is, not on its type.

The anomaly detector reads the effective values of a Screw afresh at each attempt, through effective_values.read_effective_values, which keeps nothing between two calls. So its next decision, and the parameter copy that it records, hold the new value.

The rule is a placeholder, not a regression. The new maximum dynamic torque of a Screw type is PLACEHOLDER_MARGIN (20 %) above the highest dynamic torque that the type’s ScrewIntact attempts recorded in their Disassembly phase. It shows the loop: a threshold changes from the graph’s own history, and the next decision uses it. A real regression, and the other thresholds, are left for the use case’s second milestone. The first value that the learner derives for a Screw type replaces whatever the type held, a seeded example value too, higher or lower. After that the value only rises.

It learns from the decision tree’s own outcomes. An outcome is what the detector observed, not a confirmed Screw condition. So the rule takes a ScrewIntact attempt for an intact screw, and a wrong threshold can reinforce itself. Where a confirmed Screw condition comes from is left for the second milestone too.

What it remembers is in memory: the operations it has learned from, and the value it derived last for each Screw type. A learner that starts again learns from every completed operation once more, and arrives at the same values, because the rule takes the highest torque of all of them. Each run also tells the learner’s memory (learner_memory) how it ended, each value it changed with the value the Screw type held before, and what went wrong, for its dashboard box. The value held before comes from the run’s one query, so the box reads no store.

jms_kapps.uc1.learner.placeholder_max_dynamic_torque(intact: Iterable[Frame]) → float | None[source]#

PLACEHOLDER RULE: a maximum dynamic torque PLACEHOLDER_MARGIN above the highest dynamic torque of intact, the frames of ScrewIntact attempts.

The dynamic torque is the unscrewing torque of a Disassembly sample, counted by its magnitude, as the decision tree counts it. None when no frame holds a Disassembly sample with a torque.

jms_kapps.uc1.learner.intact_attempts(db: Queryable) → list[IntactAttempt][source]#

Every unscrewing operation that is done with the outcome ScrewIntact, in one query.

An operation counts once it is done, which the detector commits together with the outcome. Only ScrewIntact ends an operation done; a failure outcome ends it failed, and it keeps the outcome. The query keeps both filters, because a graph written before that rule holds operations that are done with another outcome. One whose Screw names no Screw type, or that holds no reference, is not found. The same query reads the value of the learned threshold that each Screw type holds, one value of it, so that a Screw type with two values gives no second row.

class jms_kapps.uc1.learner.Learner(middleware: SemanticMiddleware, frames: FrameReader, memory: LearnerMemory | None = None)[source]#

Bases: object

Derives the maximum dynamic torque of each Screw type, one run at a time.

Runs do not overlap: the process makes one after another.

Parameters:

  • middleware – The learner’s own middleware instance. A run reads the graph through it, and commits through it.

  • frames – Reads an attempt’s frame from the time-series store.

  • memory – Where it keeps what it knows of its own runs, which its dashboard box shows.

learn() → dict[IRI, float][source]#

One run: learn from the attempts completed since the last run, and commit what changed.

An attempt whose curves cannot be read is logged and passed over for good: its reference names no frame that the time-series store holds, or its rows do not make one frame. Any other failure ends the run before its commit, remembers nothing of it, and the next run tries the same attempts again.

The run tells the learner’s memory that it starts, and how it ended: with how many new attempts it learned from and each value it changed, old and new, or why it failed, at which Operation’s attempt if at one. It tells it each attempt it passes over too.

Returns:

The value committed to each Screw type whose value changed. Empty when none changed, and then nothing is committed.

Raises:

  • InfluxDBError – If the time-series store refuses a read.

  • httpx.HTTPError – If the time-series store cannot be reached.

  • kapps_triplestore_interface.exceptions.TripleStoreInterfaceError – If the triple store refuses the commit.
