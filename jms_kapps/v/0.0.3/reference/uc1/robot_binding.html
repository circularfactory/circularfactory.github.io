jms_kapps.uc1.robot_binding#

How the screwing resource’s middleware instance drives the robot over MQTT: the binding of the robot’s parameters, built from the knowledge graph, and the sink that collects every sample.

The knowledge graph describes the robot of the screwing resource (:Robot1, written by the seed) as twelve parameters that a client reaches over MQTT: three readings, the attempt’s state, the start command and seven setpoints, each a parameter node one level below the robot, with its topic, its broker and its access mode (seed.robot_parameter_node). The middleware’s connector wiring recognises such a node by its property, a subproperty of the middleware’s MQTT interface property, and asks a binding descriptor for the connectors that realize it: one that reads the topic into the data model, and one that publishes the data model’s value to the set topic for a parameter a client may set. The middleware ships that descriptor, MQTTBinding, and builds twenty connectors for the robot from it: twelve read, eight write.

Use case 1’s own descriptor (robot_wiring) delegates to the middleware’s and changes one thing: the formatter of each connector. The middleware’s formatter turns a payload into the value the data model holds, and the data model holds only the latest value; an attempt needs every sample. So the descriptor wraps the formatter (TappedFormatter): each payload the read connector takes goes to the attempt’s Sink whole, with the parameter it arrived for, before the formatter takes its value out of it. The sink is thread-safe, because the connectors run on the middleware’s event loop and the attempt on the workflow’s worker thread, and gated: it keeps messages only while an attempt has it open, so a payload between attempts is dropped. The descriptor is registered in a connector registry of the screwing resource’s own, so the process-wide default registry stays as the middleware ships it. The descriptor also records each parameter it bound (BoundParameter): the setpoint writer needs the field and the node type of a parameter.

A setpoint is a persistence write that names the parameter (Setpoints, an interim helper: the middleware has no public verb for it yet). The write sets the parameter’s field on the robot’s model in the data model and tells the persistence connector which field changed, so that exactly the write connector of that parameter publishes the value to its set topic, and the data model shows the value. It runs on the middleware’s event loop, from the worker thread, through the loop that an on-start-up callback captured.

The screwing resource’s code names no broker, port or topic: every connector comes from the graph description, and the broker comes up through the transport hook the build is given (mqtt_broker.ensure_transport).

Every public name of this module is an interim name, marked so in the glossary.

Where every payload of the robot goes while an attempt collects: a thread-safe queue that the connectors fill from the event loop and the attempt drains on its worker thread.

It is open only inside open. A payload that arrives while it is closed is dropped: between attempts the robot still publishes its state, and a sample of an attempt that ended would otherwise be taken for one of the next. Opening it drains what a race left behind.

class jms_kapps.uc1.robot_binding.Setpoints(middleware: SemanticMiddleware, resource: IRI, wiring: RobotWiring, *, timeout: float = 10.0)[source]#

Bases: object

Writes a value of a parameter of the robot into the data model of the screwing resource’s middleware, so that the parameter’s write connector publishes it to its set topic. Interim: the middleware has no public verb for a write that names a parameter.

The write runs on the middleware’s event loop, where the connectors run: it reads the resource’s model from the persistence connector, sets the parameter’s field on the robot’s model to a node holding the value, and hands the model back with the field named as what changed. The persistence connector then notifies the connectors of that field alone, and of those only the write leg publishes; the data model shows the value from then on. The loop is the one the middleware runs its start-up callbacks on, captured there; a write before the middleware has started raises.

Parameters:

  • middleware – The screwing resource’s middleware instance.

  • resource – The screwing resource, the root of the data model.

  • wiring – The wiring that holds each bound parameter: its field and its node’s shape.

  • timeout – How long the worker thread waits for the loop to finish one write.

write(parameter: IRI, value: object) → None[source]#

Write value as the value of parameter of the robot.

Raises:

  • RuntimeError – If the middleware has not started, if this is called on the event loop itself (where waiting for the loop would never end), or if the write did not finish within the timeout.

  • KeyError – If the middleware built no connector for parameter.
