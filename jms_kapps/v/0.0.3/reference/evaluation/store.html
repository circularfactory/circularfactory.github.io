jms_kapps.evaluation.store#

The store of one run: a repository of its own on the configured GraphDB, and the guard around it.

One repository for each run. A run creates a repository named eval- plus its run id, through GraphDB’s REST API, from jms_kapps’ repository config, graphdb/jms-kapps-repo-config.ttl: with SHACL on, the config with only its id changed; with SHACL off, the twin, which also drops the SHACL layer around the store, so that it differs from jms_kapps’ config only in that layer and the id. Both run the ruleset rdfsplus-optimized: a config with another ruleset is refused before it is sent, and so is a repository for which the store answers another ruleset. The run deletes its repository at its end, also after a failure, and never any other.

The guard. Every request the server sends goes through permit, which holds an explicit list of the requests a run may send, each by its method and its path. A request that names a repository is one of two kinds. The monitoring view of a repository (GET rest/monitor/repository/<id>) may name any repository of the server, the protected ones included (monitorable); it only reads the counters of queries, transactions and connections. Everything else that names a repository, reads of its config and of its size and the creation and deletion, takes only guarded: eval- plus a run id of letters, digits, - and _. guarded refuses jms-kapps, the repository of the demonstration, kapps-demo, the middleware’s, and Tests, the live suites’ of every library, in any spelling, and every name without eval-. So every write, and every read of data (a query, the statements, an export, the size of a repository), is refused for any repository but the run’s own. A refused request is not sent. The server deletes only a repository that it created itself in this run.

What the Workbench shows. The facts a record holds of the server are the answers of the REST views that the GraphDB Workbench reads, each kept whole as the server answered it, with its status (View): the version and the edition, the repositories, the resource view and the structures view (Monitor, System), the license, the run’s own repository, its config, its size and its query and transaction view, and the query and transaction view of every other repository. A view that the server refuses is kept with its status and why, and the run goes on: the harness invents no fact.

The login is the triple-store interface’s, POST rest/login, with the connection variables GRAPHDB_URL, GRAPHDB_USERNAME and GRAPHDB_PASSWORD, which the command reads. Neither the user nor the password is kept anywhere a record reads.

The store helper (interim names) jms-live-store reuses the login, the guard and the config rewrite for the store chores of a /land live check. The guard’s prefix is a parameter (guarded, permit, repository_config, GraphDBServer(prefix=…)), eval- by default, so the harness is unchanged; the helper passes ogm-disposable-. Two exceptions serve the helper alone and are off by default: size_of_any lets the size of any repository be read (the tripwire reads jms-kapps and Tests), and adopt holds a repository that another process created as one to delete. login and token are public for the helper.

jms_kapps.evaluation.store.permit(method: str, path: str, own: Collection[str] | None = None, *, prefix: str = 'eval-', size_of_any: bool = False) → None[source]#

Let a request through: only the requests of the list below, and nothing that a pattern could also match a write with.

  • GET of a view in SERVER_VIEWS;

  • GET rest/monitor/repository/<id> of any repository (monitorable);

  • POST rest/repositories, the creation of a repository (the caller checks its config names the run’s own);

  • GET rest/repositories/<id> and GET rest/repositories/<id>/size of the run’s own repository, and DELETE rest/repositories/<id> of the run’s own (guarded).

Parameters:

  • own – The repositories that are the run’s own, where the caller knows them: a repository of the eval- form that is not among them, another run’s, is refused too.

  • prefix – The prefix of the repositories the caller may create and delete (guarded).

  • size_of_any – Whether GET rest/repositories/<id>/size may name any repository (monitorable), as the store helper’s tripwire reads the shared ones.

Raises:

StoreRefused – If the request is none of these, or names a repository the list does not allow it to.

jms_kapps.evaluation.store.repository_config(repository: str, *, shacl: bool, source: str | None = None, prefix: str = 'eval-') → str[source]#

The config of the run’s repository repository, as Turtle: jms_kapps’ config with its id changed, and without its SHACL layer unless shacl.

The SHACL layer is the rdf4j:ShaclSail that jms_kapps’ config puts around the store’s own sail, with every setting of its own. The twin points the repository at the store’s sail directly; nothing else changes, not even the label.

Parameters:

  • source – The config to start from, jms_kapps’ if None.

  • prefix – The prefix repository must have (guarded).

Raises:

StoreRefused – If the guard refuses repository, if the config does not name one repository with a store’s sail in it, or if its ruleset is not rdfsplus-optimized.

class jms_kapps.evaluation.store.GraphDBServer(url: str, *, username: str, password: str, client: Client | None = None, timeout: float = 60.0, prefix: str = 'eval-', size_of_any: bool = False)[source]#

Bases: object

GraphDB’s REST API, as a run uses it: create, read and delete the run’s own repository, and read the views the Workbench shows.

Every request it sends is kept in requests, by its method and its path, so that a record shows that no request named a repository other than the run’s own.

Parameters:

  • url – The server, GRAPHDB_URL.

  • username – The login’s user, GRAPHDB_USERNAME.

  • password – The login’s password, GRAPHDB_PASSWORD.

  • client – The HTTP client, one of its own if None: a test’s stand-in of the store.

  • timeout – How long a request may take, in seconds.

  • prefix – The prefix of the repositories it creates and deletes (guarded).

  • size_of_any – Whether it reads the size of any repository, not only its own.

repository_monitors(repositories: dict[str, Any]) → dict[str, dict[str, Any]][source]#

The monitoring view of every repository that the view repositories (the server’s list) names as RUNNING, by its id, the protected ones included. A repository in any other state, or in none, is kept with its state and marked as not read, and no request names it: the view of an inactive repository might initialise it, which would load another user’s repository into the shared server, and an inactive repository has no queries, transactions or connections to count. Empty where the list was refused: the refusal is in the list’s own view.

round_trip() → dict[str, Any][source]#

One round trip: how long the server takes to answer its version, in milliseconds, with the status it answered. It never raises: a refused or lost read is kept as such.

round_trip_ms(times: int = 5) → list[float][source]#

How long the server takes to answer its version, times times one after the other, in milliseconds: the network’s round trip and the server’s least work. The login comes before the first, so that no time counts it.

Create the run’s repository repository from config, a repository config in Turtle.

A repository of that name that exists already is not this run’s, and is refused. Where the store’s answer is lost, the repository is this run’s if the store lists it then, so that the run deletes it.

deleted_after_a_lost_answer(repository: str) → bool[source]#

Whether the store deleted the run’s repository repository although the deletion got no answer (the request did not reach the store, no answer came in the request’s time, the connection dropped, or a gateway answered in the store’s place, AnswerLost): one list of the server’s repositories, by a request that names none, as the creation does after a lost answer.
