jms_kapps.evaluation.sweep#

jms-eval-sweep: the runs of a spec, one by one, each a UC2 run of one configuration on its own repository of the configured GraphDB, with its record (jms-eval-uc2). Iteration one of the measurement harness.

jms-eval-sweep <spec.toml> [–runs <folder>] [–prefills <folder>]

[–configurations 1-9,12] [–repetitions 1-3] [–set KEY=VALUE …] [–list] [–heavy-run-approval “<who>, <when>”] [–stop-at <time>] [–repeat block3:2,7:2]

It reads the spec (spec), with each –set over its values, and runs each selected repetition of each selected configuration, in the spec’s order: the repetitions of one configuration one after the other. –configurations and –repetitions select by number, from 1, in the order –list shows; without them every run of the spec is selected.

A run whose record exists is skipped, so that a sweep continues in a later time window: a record below –runs that says it is that repetition of a configuration with the same values (spec.SpecConfiguration.key). A run that failed is skipped too: a failure is a result. A run that a stop signal ended is no measurement: its record’s outcome is interrupted, and the next call makes the run again, in a folder of its own, beside the interrupted attempt’s, whose record stays as it is.

The precision rule and the rounds (interim names). A spec with a [precision] table gives no fixed repetitions to its configurations at normal load: each runs until the rule holds (precision), at most 20 times, in rounds (rounds). A round makes one run of each selected configuration that is still open, in the spec’s order: round k makes repetition k. A configuration is open while it does not meet the rule and has made fewer than 20 runs (rounds.is_open); one whose throughput median is 0 once it has its minimum of valid runs stops there. One call goes on round after round (sweep_rounds) until one of its ends: the stop time, the stop file, or the end of the rule, where no selected configuration is open. The state is in the records, as above: a call that stops goes on at its round in the next call, an interrupted attempt is made again and does not count toward the 20, a call with a smaller –configurations leaves the configurations it no longer selects as they are, and –repetitions narrows the rounds to those of its repetitions. Removed configurations: –remove 3,7 records configurations by their keys in removed-configurations.json in –runs, and every later call of this command and of jms-eval leaves them out, whatever it selects, until –put-back 3 puts them back; both run nothing, and –list shows each removed configuration as removed. A running call reads the file again before each round. A record holds sweep.repetitions 20 and sweep.round; a record made in a pass before the rounds keeps its sweep.pass, and its run counts as its repetition. –list shows the next round and, for each configuration, its runs made, its valid runs and whether it is open.

The heavy parts in the rounds (interim names). A ramp, a replay and a sustained load (a heavy configuration that is no ramp’s level) each run one time, in round 1, at its place in the spec’s order (heavy_parts, chosen_runs, replays_due): a ramp at its block’s place, its rates rising, until it ends by its rule; a replay right after its configuration’s first valid run, its factors rising, until its first broken level; a configuration without a valid run keeps its replay for the round that makes one. A later round makes no level of one that ended, and goes on with one that a round left unfinished, from its lowest level without a record. –repeat block3:2,7:2 makes sure a target repetition of each heavy part it names exists: ramps by their block, replays and sustained loads by their configuration’s number (both for a heavy configuration with replay factors). While a part’s last repetition ended below its target, the next round makes one more, from the lowest level until it ends, under the same approval, and its records say sweep.repetition 2 (then 3); a repeated replay replays the run that its first repetition replayed. A target that exists or is under way makes nothing, so a restart with the same command line is safe. A target whose next repetition –repetitions leaves out makes nothing in that call, which says so and goes on. A heavy configuration of such a spec with repetitions other than 1 is refused (spec). –list shows where each heavy part stands.

The stop time and the stop file (interim names). Before each run, a replay level too, the call checks its stop time, –stop-at (a date and time with its zone, such as 2026-10-14T06:00+02:00), and the stop file, STOP in –runs. At the stop time, or where the stop file is there, it stops before that run; a run that started before the stop time runs to its end. A call that stops at the stop file removes it, and a call that ends another way removes a stop file that came meanwhile, so that it never stops the next call. So a person removes configurations at any run: make the stop file, wait for the call to stop, remove them with –remove, and call the sweep again; the next call goes on at the round that the records show. Both hold for a spec of fixed repetitions too. A round that has nothing to make, since the rule cannot read records that name its runs, ends the call with its own message.

The series (interim names). –list and each run line, a replay level’s lines too, show a configuration’s number with the spec’s series (spec.SpecConfiguration.name), such as “before 7”; a record, a run’s folder and the options that select (–configurations, –remove, –put-back, –repeat) keep the number.

The pick seed. Repetition k of every configuration takes the seed pick_seed(base, k) for the WarehouseManagementSystem’s picks: the base is the spec’s pick_base_seed, else the fixed DEFAULT_BASE_SEED, so repetition k has the same seed in every configuration and the repetitions of two configurations stay paired. The seed is written into the run’s saved configuration as a run setting, outside the configuration’s key, and into its record; jms-eval-uc2 run on that saved configuration makes the same picks.

Before the first run it refuses a spec in which a configuration misses a value, naming the value, and it resolves each selected configuration that has a run to make, so that a file it names that is not there, or a strategy that is not found, is refused before anything reaches the store. It refuses a configuration with the wrapper where OpenTelemetry, the extra evaluation, is not installed.

A heavy run (heavy = true: a sustained load or a ramp’s level) runs only under an approval that covers it (approval): the option –heavy-run-approval gives the approval file, which any person may give for one spec and one period, in agreement with the server’s admins. Inside the period the sweep runs every heavy configuration of the approved spec under that one approval, several ramps and sustained loads alike. Each heavy run is checked at its start, and one that no approval covers then is skipped and listed: where there is no approval, the period is not now, the spec is another or changed since it was approved, or the call has –set overrides, which no approval covers. The sweep goes on with the next run, a skipped level of a ramp or a replay skips its higher levels in that round, and at its end the call lists each run it skipped with the reason. A skip writes no record, so a later call whose approval covers the run makes it; a call that only skipped heavy runs exits as if they were not selected. A run at normal load needs no approval, and the heavy switch is off by default. Each heavy run’s record keeps the whole approval.

A ramp (spec, ramp) runs its rates one per run, in rising order, and a selection with a level of a ramp whose lower levels have neither a record nor a run to make is refused, since a ramp judges each rate before the next. After each run the sweep judges the level with the broken rule, and it stops the ramp at the first level the ramp ends at, a broken one or one with no run that counts: the ramp’s higher rates are not run, and the sweep goes on with the runs after them. A plateau or a UC2-limited level breaks nothing, so the ramp goes on past it (ramp). A ramp that ended in an earlier call sends no higher rate either; under the precision rule a repetition on request starts again from its lowest rate, and each repetition is judged apart.

A failed run does not stop the sweep; 3 failed runs in a row do: one failed run at night must not end a series that runs with no person present, so the sweep goes on after a failed run, and stops after FAILED_RUNS_IN_A_ROW failed runs one after the other, so that a store that refuses every run is not sent the rest of the spec. A run counts as failed where its outcome is failed or failed over time, or where the records do not show it after the call made it, right after the run or when the call chooses its next round: the call then leaves its configuration out for the rest of the call. A completed run whose repository the store did not delete counts too and resets nothing; any other completed run, valid or invalid, resets the count. A run that a stop signal ended (Ctrl+C, SIGTERM or a closing terminal’s SIGHUP) stops the call at once. The next call skips a failed run and goes on after it, and makes an interrupted one again.

The replay levels (interim names). A block of the spec may give replay_factors (spec). After the UC2 runs of each configuration of that block the sweep replays the first valid run of that configuration, with the store-only baseline (baseline), once per factor in rising order, each level on a repository of its own (replay_levels). A level is a run of the run kind baseline whose record says sweep.key, the configuration’s key and the factor, and holds the level’s numbers (replay_level). After each level the sweep reads whether it is broken, and the replay of that configuration stops at its first broken level: the higher factors are not run, in this call or a later one. A level that failed ends the replay too, and counts toward the failed runs in a row. Every factor above 1 is a heavy run and runs only under an approval that covers the spec and the replayed configuration, exactly as a heavy configuration does (approval.cover): a level above 1 that none covers at its start is skipped and listed, with its higher levels, and so is a level that cannot start. A factor of 1 is a replay at normal load. The rounds of the precision rule plan a replay as a heavy part (above): in round 1, right after its configuration’s first valid run, and later only while it has not ended or has a request; a level’s record says the replay’s repetition. –list shows each configuration’s levels.

The report (report, jms-eval-report) is made again after each run, right after the run returns and before the sweep judges how it ended, whatever the end: completed, invalid, failed or interrupted. It is made with the sweep’s –set overrides, into report/ below –runs. An error of the report is told on the sweep’s output and never stops or fails the sweep.

It exits with 0 once every selected run has its record, or no selected configuration under the precision rule is open, or it stopped at its stop time or at the stop file, and every run it made completed; 1 when a run it made failed, when it stopped at a run that a stop signal ended, at the third failed run in a row, by a stop signal between two runs, or at a round with nothing to make; and 2 when it refused to start: nothing reached a store then. A heavy run that it skipped changes no exit code. –remove and –put-back exit with 0 once the removed configurations are written. –list shows the spec’s configurations and their runs, and runs nothing, so it needs no store.

The connection to the configured GraphDB is that of jms-eval-uc2.

Make each of runs_to_make that is not skipped, one by one, and stop where stops says so before a run, at a run that a stop signal ended, or at the third failed run in a row. Returns how it ended (Ended): MADE where it went through every run.

A failed run does not stop the sweep: it goes on, and stops after FAILED_RUNS_IN_A_ROW failed runs one after the other, so that a store that refuses every run is not sent the rest of the spec. A run counts as failed where it did not complete (failed, or failed over time), or where the records below runs do not show it after it was made: its configuration is then left out for the rest of the call. A completed run whose repository the store did not delete counts too, and does not reset the count; any other completed run, valid or invalid, resets it. A run that a stop signal ended stops the call at once.

A heavy run that no approval covers at its start is skipped and listed: each heavy run is covered at its start (SweepRun.heavy, HeavyCheck.cover, with the time of stops), and one that is not covered then (no approval, another or a changed spec, a period that is not now, –set overrides) is skipped, with no record, and the sweep goes on with the next run. A skipped level of a ramp or a replay skips its higher levels in this round. A replay level that cannot start is skipped and listed the same way.

After each run of a level of a ramp it judges the ramp with the broken rule (ramp.judge), from its runs below runs and the one just made, and where the ramp ended, it skips the ramp’s higher levels and goes on with the runs after them.

A replay level (SweepRun.replay_factor) replays the first valid UC2 run of its configuration below runs with run_replay; after it the sweep reads whether the level is broken, and where it is, it skips the configuration’s higher levels. A configuration with no valid run to replay has its levels left, and the sweep says so.

Parameters:

  • found – The spec’s configurations, of which a ramp’s levels are judged.

  • run_replay – Makes one replay level: the configured store’s by default.

  • stops – The call’s stop time and stop file, checked before each run, and its clock, which a heavy run is covered at.

  • made_runs – Where each UC2 run made is added, by its configuration’s key and repetition.

  • unattended – What the call keeps from run to run (Unattended): a new one by default.

What one call of the sweep chooses next (interim names; choose_call).

chosen are the runs it makes or skips, in the spec’s order, and replays the configurations whose replay levels it plans, with the factors it plans. the_round is the round of the precision rule it makes next, or None. done and summaries are what the records below the runs’ folder say.
