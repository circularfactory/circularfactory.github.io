jms_kapps.evaluation.spec#

The spec of a sweep of the measurement harness, iteration one: which configurations a sweep runs, and how often each.

A spec is a plain TOML file of sweep blocks, with defaults of its own:

[defaults]                      # the spec's own defaults, for each of its configurations
boxes_per_minute = 30
warm_up_seconds = 60
window_seconds = 300
drain_bound_seconds = 300
matcher_interval_seconds = 2
transit_seconds = 3.0
retry_seconds = 1.0
heavy = false
repetitions = 5
pick_base_seed = 20261012       # optional: the base of each repetition's pick seed

[[sweep]]                       # one sweep block: the cross product of its axis values
topology = ["cross", "grid"]
prefill = ["{topology}-1k.ttl", "{topology}-1M.ttl"]

A block’s keys are those of a configuration (configuration.KEYS) and repetitions, each with one value or a list of values: the block is the cross product of its lists, the first key varying slowest. A block with no key at all is one configuration, of the defaults alone.

Precedence. A value comes from the command’s defaults (COMMAND_DEFAULTS: the strategies real, SHACL on, history collection off, no prefill, the wrapper on, the transit time 3.0 s, the retry wait 1.0 s, 1 repetition), then the spec’s defaults, then its block, then a flag of the command (setting), each over the one before.

The pick seed (interim names). Repetition k of every configuration gets the seed pick_seed(base, k) for the WarehouseManagementSystem’s picks, so that the repetitions of two configurations stay paired. The base is pick_base_seed of the spec’s [defaults], a whole number, or else the command’s fixed DEFAULT_BASE_SEED. The seed is no key of a configuration and no part of its key: all repetitions of a configuration keep one key. The sweep writes it into each run’s saved configuration.

The prefill seed (interim name). jms-eval makes each prefill file that a spec names and that is missing (harness), with the seed 1 unless the spec’s [defaults] give prefill_seed, a whole number from 0. Like the pick base seed it is no key of a configuration and no part of its key.

The series (interim name). The configuration numbers of two specs point to different configurations: configuration 7 of the iteration-one spec is not configuration 7 of the “after” spec. So a spec names its series in its defaults, series = “before”, a text, and the readers and the sweep show each number with it, “before 7” (SpecConfiguration.name). A spec without the name takes its file name without the extension. Like the seeds, the series is no key of a configuration and no part of its key; the records match by their key as before, and a run’s folder, a record file and –configurations keep the number.

The configurations of a spec are the union of its blocks, in the listed order, with no duplicates: a configuration that a block lists again keeps its place and its number. Each has its number of repetitions, and one listed again with another number of them is refused. So a spec lists the configurations it runs first in blocks of their own, and its design in blocks after them, which repeat them without running them twice.

A missing value is refused before any run starts: every value that is not a default of the command comes from the spec or a flag, and the refusal names the block and the value.

A prefill file is for one topology, so a prefill may name its topology’s name with {topology}: a shipped topology’s name, or a topology file’s name without its suffix (../topologies/grid-60.json gives grid-60).

Paths. A topology file is read from the spec’s folder, as a configuration reads its own; a prefill file from the prefills folder of the command, since a prefill file of 10M statements is no file to keep beside a spec. Neither needs to exist until its configuration resolves (resolved), just before the sweep’s first run.

The key of a configuration is a digest of its values as the spec gives them, the prefill’s topology filled in, with every number as a float: so a run is found again when the spec lists its configuration elsewhere or writes 60 as 60.0, and where the spec, the checkout or the prefills folder moved.

A ramp is a block marked as a ramp, ramp = true, whose only axis is its box rates, rising:

[[sweep]]
ramp = true
topology = "grid"
prefill = "{topology}-1M.ttl"
boxes_per_minute = [10, 20, 40, 80, 160, 320]
repetitions = 1

Each rate is one load level, made by one run, so a ramp has 1 repetition. Its runs are heavy: its configurations take heavy = true whatever the spec’s defaults say, and a ramp whose block or a flag says heavy = false is refused. They run with the wrapper, since the broken rule reads the measures that need it (ramp). A ramp’s configurations are its own: one that another block lists too is refused.

The precision rule (interim names). A spec with a [precision] table does not give a fixed number of repetitions to its configurations at normal load: each runs until the rule holds (precision), in rounds (rounds), at most maximum_runs times.

[precision]                     # every key is optional; these are the values
latency_tolerance = 0.10        # the bootstrap interval of the pooled commit p95 within +-10 %
throughput_spread = 0.10        # the IQR of the transports ended per minute at most 10 % of the median
minimum_runs = 10               # valid runs needed, from 2: from at least two rounds
maximum_runs = 20               # runs made at most

These are settings of the spec outside a configuration’s key. A table that gives pass_sizes is refused: the rounds replaced the passes. A configuration under the rule is one that is neither a ramp’s level nor heavy; its repetitions is maximum_runs, and the spec, a block or a flag that gives it repetitions is refused. A ramp’s level and a heavy configuration are heavy parts (heavy_parts): each runs one time, in round 1, and again on request, so one with repetitions other than 1 is refused.

Replay factors (interim names). A sweep block may list the factors by which the store-only baseline replays a recorded run compressed in time:

[[sweep]]
topology = "grid"
prefill = "{topology}-1M.ttl"
boxes_per_minute = 30
replay_factors = [1, 2, 4, 8, 16]

After the UC2 runs of each configuration of the block, the sweep replays the first valid run of that configuration once per factor, in rising order (replay_levels). The factors are a setting of the block, outside the configuration’s key and no axis of its cross product: a configuration that a later block lists again gets the factors of both. Each is a number from 1; a replay needs the store requests of a run with the wrapper, so a configuration with factors has wrapper = true. Every factor above 1 is a heavy run (approval). Each level has a key of its own, the configuration’s key and the factor (replay_levels.level_key).

class jms_kapps.evaluation.spec.PrecisionRule(latency_tolerance: float = 0.1, throughput_spread: float = 0.1, minimum_runs: int = 10, maximum_runs: int = 20)[source]#

Bases: object

The settings of the precision rule that a spec’s [precision] table gives (interim names).

A configuration meets the rule when it has minimum_runs valid runs, the bootstrap 95 % interval of its pooled commit p95 lies within latency_tolerance of the p95 on both sides, and the IQR of its transports ended per minute is at most throughput_spread of their median. At most maximum_runs runs are made of it. The sweep works in rounds (rounds): round k makes repetition k of each configuration that is still open, so the last round is maximum_runs.
