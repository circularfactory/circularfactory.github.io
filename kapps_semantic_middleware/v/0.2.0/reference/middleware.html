KAPPS Semantic Middleware.

Extends transitional_sync_middleware.Middleware with knowledge-graph registration, discovery, and execution capabilities. Supports three modes – see modes.Mode for what each one means and which are implemented.

Bases: Middleware

KAPPS Semantic Middleware extending transitional_sync_middleware.Middleware.

Adds knowledge-graph registration, discovery, and execution. It supports the three modes of Mode. Resource mode registers the Service/Workflow/Capability instances on startup, and deregisters them on shutdown. It is the only mode with runtime consequence today.

mode accepts a Mode constant or the equivalent bare string – Mode is a str subclass, so existing mode="resource" callers are unaffected.

Operation execution: an Operation resolves via its implemented Capability to a Workflow endpoint, which is then invoked over HTTP.

APP_TITLE = 'semantic-middleware'#

What this product calls itself. The base class names the framework it is built on, which is accurate for the framework and wrong for anything hitting our address – a visitor landing on a middleware instance should be told what it reached. The dependency policy allows only bugfixes in sibling repos, so the name is corrected here rather than there: the base class stays as it is, and every override lives on this side.

property app#

The FastAPI app, with its root route renamed and a quiet favicon route added.

The base class registers GET / inside its own app property, so the route exists the moment the app does. Starlette matches routes in order and a second registration would never be reached, so the original is removed rather than shadowed. Guarded by a flag: the base property caches, but this one is consulted on every access, and neither patch below may run twice on the same app object.

The favicon route answers GET /favicon.ico with a bare 204: this product ships no icon asset, and every browser that requests one otherwise logs a 404 – the only console error a control station or a unit middleware’s page would otherwise show on a clean load.

The nested root function handles GET / requests. It returns the welcome message defined in APP_WELCOME.

The nested favicon function handles GET /favicon.ico requests. It returns an empty 204 response to suppress browser console errors.

commit(*instances: str, class_scope: Any = None, entry: Sequence[Create | Update] = (), exit: Sequence[Create | Update] | Callable[[], Sequence[Create | Update]] = (), error: Sequence[Create | Update] | Callable[[BaseException], Sequence[Create | Update]] = ()) → _Commit[source]#

A state transition that the store admits before the work it describes begins.

Usage, inside a coroutine:

running = [Update(instance_iri=op, data={str(SVC.operationStatus): ["running"]})]
done = [Update(instance_iri=op, data={str(SVC.operationStatus): ["done"]})]
failed = [Update(instance_iri=op, data={str(SVC.operationStatus): ["failed"]})]

async with mw.commit(
    op, class_scope=scope, entry=running, exit=done, error=failed
) as transition:
    torque = await robot.screw(transition.node.instance)  # the physical work
    transition.update(op, {str(SVC.executionResult): [torque]})

and the same with with in code that runs in a worker thread, such as a callback, a notification handler or a script. entry, exit and error are lists of kapps_ogm Create and Update changes. Each is written as one OGM.commit, so each may span several instances. Nothing here is specific to a vocabulary: any datamodel and any state transition fit.

  • Entry. The entry transition is committed. If the store refuses it, its error is raised, nothing is written, and the body does not run. Then each of instances is fetched for the body: materialized under class_scope when one is given, else as a reference. They are transition.nodes by IRI, and transition.node when there is one.

  • Body. Domain code, such as a robot’s move. It holds no transaction and no connection of the triple store, so heartbeats and other writes go on while it awaits. A body that blocks its thread (time.sleep, a blocking driver call) must run in a worker thread, with the synchronous with inside that thread, as callbacks and notification handlers run. Only transition.update(instance, {property: [values]}) changes the graph, at the clean exit. A change made to transition.node or to its .instance is not committed, and an assignment to an attribute that the transition does not have raises AttributeError.

  • Clean exit. The body’s changes and the exit transition are committed as one OGM.commit. Changes to one instance that a change names merge into one change, because kapps_ogm refuses two changes that write one instance. A body that sets a property that the exit transition also sets, on the same instance, wins: its value is committed and the exit transition is skipped as a whole. So a body that sets the status itself keeps it. The merge does not reach a named instance that a change only nests with properties: when two changes both write one, kapps_ogm raises ValueError at the exit, which commits the error transition and then raises.

  • Error in the body. The body’s changes are dropped, the error transition is committed, and the error is raised again. An error of the fetch after the entry is handled the same way, and the body does not run.

  • Refused exit. The error transition is committed, and the store’s error is raised.

exit may be a function that returns the changes, called at the clean exit, so the exit transition can depend on what the body did. error may be a function that takes the exception and returns the changes. If the error transition itself fails, the original exception is raised, with a note and a log record that say so.

A cancellation of the body under async with (a deadline of anyio.fail_after or move_on_after that runs out, a cancelled task) is an error of the work: the error transition is committed in a shielded cancel scope, so the cancellation cannot interrupt it, and then the cancellation is raised again. error receives the cancellation exception. An interrupt or an exit (KeyboardInterrupt, SystemExit, GeneratorExit) writes no transition, in either form: the entry transition stays, as after a crash. The exit of the asynchronous form is shielded too, so a deadline that runs out after the body finished does not stop its exit commit.

Inside a coroutine, use async with. It runs every graph call (the commits, the fetch and the transition functions) in a worker thread, so graph I/O never blocks the event loop. The synchronous form makes the same calls in the calling thread and blocks it. Nothing stops it from being used on the event loop, where it stalls every other task, heartbeats included.

The write goes to the graph only. All changes go to this instance’s named graph. The datamodel that this instance serves over REST does not change, and no synced connector hears of the write, so no device is written.

An Operation’s issuer is notified. A write can move an Operation that has an issuer (svc:issuedBy) to running, done or failed. After the store admits such a write, the middleware hands the notification to a background worker of this instance and goes on at once. The worker reads the issuer and notifies it, as notify() does, in the order of the writes. If the issuer cannot be notified, a WARNING is logged and nothing is raised, because the write has happened.

kapps_ogm’s rules apply. A Create that carries data must carry its own class_scope: otherwise ValueError is raised before it is written, in the entry before any write, and in the exit transition at the exit. The store refuses a commit whose precondition is false with PreconditionFailedError, and writes nothing of it: a Create of an instance that the store already holds, or a change that removes a value that is no longer there, because another write changed it after kapps_ogm read it. The error is not caught: for a Create, it signals a reused IRI.

Raises:

  • kapps_triplestore_interface.exceptions.TripleStoreInterfaceError – If the store refuses a transition. A SHACL refusal is ShaclValidationError, whose report is the store’s validation report, verbatim. A false precondition is PreconditionFailedError.

  • ValueError – If a change does not fit its class, two changes of one transition write one instance (these from kapps_ogm), or a Create carries data but no class_scope.

  • requests.exceptions.RequestException – If the store cannot be reached.

create(cls: str, scope: Any, instance_iri: str | None = None) → _Creation[source]#

Create one new instance of the class cls, built on commit().

Usage:

with mw.create(SNAPSHOT, snapshot_scope) as snapshot:
    snapshot.update({str(EX.decision): ["unscrew"]})

and async with in a coroutine, as for commit(). For new work for a resource that realizes a Capability, use request(): it creates the Operation with this method, and then notifies the receiver.

  • Entry. The IRI is minted, <class>_<12 hex>, unless instance_iri is given, and the body reads it as creation.iri: a nested creation can be linked before anything is written. A predefined scope checks its inputs here; wrong inputs raise before the body runs and before any write. Nothing is read or written.

  • Body. creation.update({property: [values]}) sets the new instance’s properties. A value that is an IRI, such as the iri of a nested creation, is a reference.

  • Clean exit, alone. One OGM.commit writes the Create of the instance, the changes of its predefined scope, and the changes of every creation nested in it. A refusal by the store raises its error, and nothing is written.

  • Clean exit, nested. Inside the body of a commit() or of another create() of this middleware whose write is still to come, the same changes join that write instead: they are admitted or refused together with it, and an error in its body drops them. A creation commits on its own inside a body whose commit has already happened, such as that of handover(), and inside a write of another middleware (another OGM or another named graph), such as a planner’s beside a resource’s in one process.

  • Error in the body. Nothing is written or joined, and the error is raised again. Nothing exists yet that could carry an error transition.

After the clean exit, creation.changes are the changes that the creation committed or joined: its Create first, then those of its predefined scope and of its nested creations.

scope is a ClassScope of the class, or a predefined scope, which brings the rules for creating an instance of its class: a domain module gives it, and it may require inputs and add changes to the same commit. The Create names every property that scope names and every property that the body sets, so kapps_ogm drops none of them.

kapps_ogm’s rules apply. An instance_iri that the store already holds is refused with PreconditionFailedError at the commit, and nothing is written.

Raises:

  • ValueError – If a predefined scope’s inputs are wrong (at entry), the body sets a property that its predefined scope sets itself, or the data does not fit the class (from kapps_ogm).

  • kapps_triplestore_interface.exceptions.TripleStoreInterfaceError – If the store refuses the commit. A SHACL refusal is ShaclValidationError, whose report is the store’s validation report, verbatim. An instance that the store already holds is PreconditionFailedError.

  • requests.exceptions.RequestException – If the store cannot be reached.

fetch(instance_iri: str, *, class_scope: Any = None, as_reference: bool = False, materialize: bool = False) → Any[source]#

Read one instance from the graph through the OGM, as a plain call.

A read has nothing to guard, so this is no context manager. It is OGM.fetch with this instance’s OGM: class_scope selects the properties to load, as_reference loads only the IRI, and materialize builds the datamodel (node.instance). It blocks while it reads, so asynchronous code calls it in a worker thread, as the asynchronous form of commit() does.

Returns:

The kapps_ogm Node of the instance.

Raises:

  • ValueError – If the store holds no class for the instance.

  • kapps_ogm.utils.errors.AnonymousNodeFetchError – If the IRI is a Skolem IRI of an anonymous node, which only its parent carries.

workflow(*args, capability_class: Any = None, workflow_class: Any = None, **kwargs)[source]#

Register a function as a REST-invokable workflow with KG registration.

In resource mode, requires capability_class and workflow_class as keyword-only IRIs (both classes must pre-exist in the ontology). Registers the REST endpoint via the base class, then schedules KG registration of the Workflow and Capability instances on startup (after the service is registered).

On an instance with a notification handler (on_notification()), a notified Operation that implements the Capability this workflow realizes runs it, with the Operation as its one argument: a kapps_ogm Node, read and materialized under the intake’s scope (operation.instance). A parameter typed kapps_ogm.Node registers as any other does, because pydantic takes a Node as it is. Its REST route is mounted too, but the framework takes a one-parameter workflow’s argument as an optional query parameter arg, not as a body: a call passes None, or a string from the query, and the framework’s type check (typeguard) refuses both, so a call over REST is answered with an HTTP 500 and such a workflow is run by the intake:

@mw.workflow(capability_class=TRANSPORT_CAPABILITY, workflow_class=TRANSPORT_WORKFLOW)
def box_transport(transport: Node) -> None:
    ...  # the work; it commits its own transitions with mw.commit()
Raises:

  • RuntimeError – If called outside resource mode.

  • ValueError – If capability_class or workflow_class is missing.

notify(*, operation: Any, resource: Any, timeout: float = 10.0) → None[source]#

Send a notification: tell resource to look at operation in the graph.

Usage:

mw.notify(operation=transport, resource=origin_module)

A notification is one-way. It names one Operation in the graph and carries nothing else: no payload, and no result. It works in both directions: down, “an Operation for you exists”, and up, “this Operation ended or changed”. The middleware writes nothing to the graph for it. The resource’s middleware takes it through its intake when it registered an on_notification handler: the exposed workflow that realizes the Operation’s Capability runs it, or else the handler gets it. It queues it when it registered no handler. A notification of an Operation that the resource issued and that is no longer queued is feedback: it wakes the Operation’s handle, the handler gets it, and it is never queued and never runs a workflow.

The call finds the resource’s live Service in the graph (one that carries an svc:address), posts the IRI to that Service’s event trigger, and returns when the receiver confirms receipt, which it does at once. It raises NotificationUndelivered when the resource has no live Service, when it has more than one (the call does not choose between them), and when the post fails, is refused, or takes longer than timeout seconds.

This is a plain blocking call. From a coroutine, run it off the event loop:

await anyio.to_thread.run_sync(
    functools.partial(mw.notify, operation=op, resource=wms)
)
request(*, capability_class: Any, operation_class: Any, operation_iri: str | None = None, target_resource: str | None = None)[source]#

Issue an Operation: new work for a resource that realizes a Capability.

Usage:

with mw.request(capability_class=cap, operation_class=op_cls) as op:
    op.data[str(EX.hasScrew)] = [{"id": str(screw)}]  # its domain fields, if any
if await op.claimed(timeout=30):
    status = await op.ended()  # "done" or "failed"

Use it for a new Operation. It is three steps, each the work of another part of the middleware: discovery, then create(), then the delivery of notify().

  • Discovery. Before the block runs, a live Service is found that realizes a Capability of capability_class (with target_resource, one of that resource). If there is none, OperationResolutionError is raised, and nothing is written.

  • The block. It sets the Operation’s domain properties in op.data, as {property IRI: [values]}, and may read op.iri. An error in the block writes nothing.

  • Create. At the end of the block, one create() of the Operation writes it, under the operation scope. It writes the type, the cfc:implementsCapability link to the Capability that discovery found, the status queued and op.data. It also writes svc:issuedBy, the issuer: this middleware’s Resource, op.issuer. The store admits all of it or none of it. A refusal is raised, and nobody is notified. An operation_iri that the store already holds is refused with PreconditionFailedError, and that Operation is not touched. If op.data sets svc:issuedBy, ValueError is raised before anything is written.

  • Notify. With the Operation in the graph, the Service that discovery found is notified, through its event trigger, and takes the Operation through its intake or its queue (see on_notification()). If the notification fails, the Operation stays queued, and NotificationUndelivered is raised. Nothing is undone: the receiver takes up its queued Operations when it starts, and the issuer is responsible for the Operation while it is queued.

After the block, op is the IssuedOperation: it waits until the Operation is claimed and until it ends. The middleware that claims it, and the one that ends it, notifies the issuer after its commit, and that notification wakes the waits.

The Operation commits on its own, also inside the block of another commit() or create(), because the receiver reads it after the notification. A create() nested in this block joins the Operation’s commit.

This is the in-process caller face — not REST-exposed.

claim_next(scope: Any = None)[source]#

Pull-and-run the next queued Operation as a transaction context manager.

Usage:

with mw.claim_next(scope) as claimed:
    claimed.result = do_the_work(claimed.operation)

It is a commit() about the Operation it claims:

  • Entry. __enter__ takes the next queued Operation from this instance’s in-memory queue (FIFO order, raises OperationQueueEmpty if none), and commits the claim, queued to running, before the body runs. If the store refuses the claim, its error is raised and the body does not run; the Operation has left the in-memory queue, and the graph keeps it as it was. Then the Operation is re-fetched under the domain-supplied ClassScope, so the body gets exactly the object shape it needs.

  • Body. It runs the work, and may set claimed.result.

  • Clean exit. done plus provenance (executedByWorkflow / executionTimestamp / executionResult) is one commit.

  • Error. On a body exception, a fetch that fails after the claim, or a refused done, failed plus provenance and the exception message is one commit, and the exception is raised. Provenance is folded into the terminal transition. On failure the CM also dumps the resource datamodel and stores it as the Operation’s svc:failureState in the same commit, so the state that produced the failure survives the exception.

  • The issuer. After the claim, and after done or failed, the Operation’s issuer (svc:issuedBy) is notified, as after any commit() that moves an Operation. The read before the claim finds the issuer, so the claim reads nothing more for it.

Two claimants of one Operation are not told apart yet: the claim of an Operation that is already running changes nothing, and the store admits it.

This is the in-process receiver face — not REST-exposed.

handover(*, mode: Any, workpiece: Any, counterpart: Any, workpiece_update: Dict[str, List[Any]] | None = None, operation: Any = None, entry: Sequence[Create | Update] | None = None)[source]#

Hand a workpiece to a counterpart: the possession changes first, then the body moves it.

Usage:

with mw.handover(mode=MES.Pass, workpiece=box, counterpart=next_module, operation=op):
    conveyor.pass_box()  # the physical move, owned by the domain

and, with more changes that must be admitted together with the possession change, such as a transport that the next module now executes:

moved_on = Update(
    instance_iri=transport,
    data={
        str(CFC.executedOn): [{"id": next_module}],
        str(CFC.implementsCapability): [{"id": next_capability}],
    },
)
with mw.handover(
    mode=MES.Pass, workpiece=box, counterpart=next_module, entry=[moved_on]
):
    conveyor.pass_box()

The entry checks two preconditions before anything is written: this resource currently possesses the workpiece (the workpiece points at a cfc:PossessionState whose possessor is this resource), and the counterpart carries the mes:hasHandoverAbility complementary to mode. There is deliberately no check that the counterpart is free: a resource may possess any number of workpieces unless a domain rule limits it.

Then the entry commits the possession change through commit(), as one commit. The workpiece’s cfc:hasPossessedWorkpiece points at the counterpart’s one possession state; workpiece_update sets more properties of the workpiece that must change together with its possessor, such as its transport state; operation, the Operation that this handover completes, becomes done; and entry, the caller’s own kapps_ogm changes, is written too. When the counterpart has no state yet, the same commit creates <counterpart>_possession and links the counterpart to it. Nothing writes the cfc:hasPossessor link of this resource, or of a counterpart that has a state.

If the store refuses the commit, its error is raised (a SHACL refusal is ShaclValidationError, with the store’s validation report as its report), nothing is written, neither the possession change nor a change of entry, and the body does not run. The body is the move: the physical transport, and any coordination with the counterpart, for example through a request(…). A clean exit writes nothing more. An error in the body is raised as it is and undoes nothing: the possession has already changed, so the caller records what really happened.

Core says that a resource and a workpiece each have exactly one possession state. That is OWL: it licenses inferences and refuses no write. What refuses a handover at commit is the domain’s SHACL shape, for example the one that allows one box on a conveyor module.

A first handover to a counterpart without a state can race another write that creates that state. Two commits that truly coincide both write the same state triples, and one state results. When the other write lands between this handover’s read and its commit, the store refuses the second creation of the state (PreconditionFailedError), and writes nothing of it. The handover then checks both preconditions again and commits once more, with the state that exists now; if a precondition no longer holds, for example because the other write handed this same workpiece, it raises HandoverPreconditionError, and the body does not run.

A second handover of the same workpiece at the same moment is refused only in part. Both pass the preconditions before either commits. Inside its commit, kapps_ogm compares the workpiece with a fresh read of it. If the other handover’s commit landed between that read and this commit’s write, the store refuses this commit and writes nothing of it, and the handover raises PossessionSwitchConflict before the body runs. Known limit: if the other handover’s commit landed before that read, this commit overwrites its possession change, both succeed, and both bodies run.

Parameters:

  • mode – This resource’s handover ability, such as MES.Pass. The counterpart must carry the complementary one.

  • workpiece – The workpiece that this resource possesses.

  • counterpart – The resource that takes the workpiece over.

  • workpiece_update – More properties of the workpiece to set in the same commit, as {property IRI: [values]}; each listed property is replaced. A value that is an IRI (an IRI or an rdflib URIRef), or {“id”: iri}, is a reference to that object. Any other value goes to the OGM as it is: a plain str is a literal, which the OGM refuses for an object property with ValueError, before any write.

  • operation – The Operation that this handover completes. Its svc:operationStatus becomes done in the same commit.

  • entry – More kapps_ogm Create and Update changes, built by the caller, that the store admits or refuses in the same commit as the possession change, before the body. A change of the workpiece or of operation belongs in workpiece_update or is made by operation: kapps_ogm refuses two changes of one instance in one commit, with ValueError.

Raises:

  • RuntimeError – If this instance is not in resource mode.

  • HandoverPreconditionError – If a precondition fails. Nothing is written.

  • PossessionSwitchConflict – If the store found the precondition of the entry’s commit false (PreconditionFailedError, the cause). Usually another write changed what the entry had read, such as a second handover of the workpiece. The store does not say which part of the commit failed, so the same error covers a change of entry that creates an instance that the store holds. Nothing is written, and the body does not run.

  • ValueError – If workpiece_update names cfc:hasPossessedWorkpiece, which the handover sets itself, or a value that does not fit its property, or a change of entry does not fit its class or writes an instance that the commit already writes, or the counterpart has more than one possession state. Nothing is written.

  • kapps_triplestore_interface.exceptions.TripleStoreInterfaceError – If the store refuses the possession change; a SHACL refusal is ShaclValidationError. Nothing is written, and the body does not run.

register_callback(callback: Any, scope: Any = None) → None[source]#

Register a domain work callback fired on enqueue.

callback is the work function callback(operation) -> result. It runs the Operation’s work, and returns the value recorded as svc:executionResult. On each enqueue, The middleware drives a background pull-and-run around it: with claim_next(scope) as c: c.result = callback(c.operation). The middleware handles status (running->`done`/failed) and provenance. The domain writes only the work. Opt-in: with no callback registered, an enqueued Operation stays queued for a manual claim_next. scope is the domain ClassScope used to re-fetch the Operation. An instance with a notification handler (on_notification) takes its notifications through the intake, not the queue, so registering both raises RuntimeError.

on_notification(handler: Callable[[Any], Any], class_scope: Any = None) → None[source]#

Take this instance’s notifications through the intake, with handler as fallback.

Usage:

def on_transport_ended(transport):
    ...  # the Operation object; write through mw.commit()

mw.on_notification(on_transport_ended, class_scope=transport_scope)

A notification arrives at this resource’s event trigger: from a peer’s notify, from a peer’s request(), which notifies the resource it dispatched an Operation to, or from the middleware that claimed or ended an Operation that this resource issued. The trigger reads the Operation once and answers at once. The Operation then enters this instance’s FIFO, and one worker runs one Operation at a time, in arrival order:

  • An Operation whose Capability is one of this instance’s own (matched in memory, by IRI) runs the exposed workflow that realizes it (workflow()), with the Operation object as its argument.

  • Any other Operation goes to handler(operation), the fallback, such as the up direction: “this Operation ended”. So does an Operation that this instance issued to a Capability of its own, once it is no longer queued: that notification is the feedback of its own claim or end, and the workflow does not run it again.

The Operation object is a kapps_ogm Node, read and materialized under the scope: the Capability that the Operation implements and the Workflow that realizes it, united with class_scope, this subproject’s own ClassScope of the Operation. An Operation that waited behind another one is read again before it runs, so it is never stale. The middleware writes no status and no provenance: the workflow or the handler commits its own transitions with mw.commit().

A function may be a plain function or a coroutine function. A plain one runs in a worker thread, so it may block (graph I/O, a physical move) without stalling the server. A coroutine function runs on the event loop and must not block. An exception is logged, nothing is written for it, and the next Operation runs.

At startup, this instance’s own queued Operations go into the FIFO again, and its own orphaned running ones become failed, as crash recovery.

An instance takes its notifications either here or through the dispatch lifecycle (register_callback, claim_next), not both: registering one when the other is registered raises RuntimeError. One handler per instance: a second call replaces the first. Register it before the instance starts.

The Operation that request() issues: its draft in the block, its handle after it.

request() makes it; a caller does not. In the block of with mw.request(...) as op:, op.data takes the Operation’s domain properties, as {property IRI: [values]}. op.iri is the Operation’s IRI. After the block, the Operation is in the graph, queued. op.issuer is its issuer: the Resource of the middleware that issued it. svc:issuedBy records it. Then op waits for the Operation, in a coroutine:

if not await op.claimed(timeout=30):
    ...  # nobody claimed it in time: it is still queued, and still the issuer's
status = await op.ended()  # "done" or "failed"

and with op.wait_claimed(timeout) and op.wait_ended(timeout) in code that may block, with the same results.

A wait reads the status from the graph first, so a claim that came before the wait is seen. Then it waits until a notification of the Operation arrives at the issuer’s event trigger, and reads the status again. The middleware that claims the Operation, and the one that ends it, sends that notification after its commit. When the timeout passes, the wait reads the status once more. Nothing else wakes a wait: it does not poll. So a wait ends before its timeout only when the issuer’s middleware is served, and has exactly one live Service.

A middleware instance mode. Each member below says what it means.

RESOURCE = 'resource'#

Wrap one resource_iri. Register a Service. Serve its workflows and parameters. Hold a heartbeat. This is the only mode with runtime consequence today.

SERVER = 'server'#

Reserved. Serve data with no physical resource. Not implemented. Construct one raises. Out of scope for the scenario-3 controller: a controller consumes a graph, and it does not serve one.

WATCHDOG = 'watchdog'#

Reserved. Sweep liveness from a central point. Sweep stale Services. Register nothing of its own.
