When a call fails: the error map#

This page tells a consumer of the KAPPS stack what to do when it catches an error. It covers the three layers: kapps-triplestore-interface (the interface), kapps-ogm (the OGM) and kapps-semantic-middleware (the middleware). It describes the error types of interface 2.3, OGM 0.4 and middleware 0.3, and the changes that the next releases plan.

The rule#

Currently the user/consumer interprets errors, not KAPPS. Therefore KAPPS passes all errors along transparently. Interpretation, and therefore modification, of errors is fog in the far future.

The map does not change an error. It tells a consumer what it can do with one. Two rules follow from the first:

  • No layer raises a lower layer’s error again as its own type. A library raises its own type only where it detects the condition.

  • A message stays as the layer that detected the condition wrote it, and a store report stays raw.

Five actions#

Each error asks for one of five actions.

What happened

Repair

The tool or its deployment is broken: configuration, credentials, rights, an ontology that the OGM cannot map, a missing optional extra, an internal fault.

The operator. The KAPPS maintainers, for a bug.

No, not before the repair.

Retry

This attempt failed for a temporary reason: the store is unreachable or slow, or a peer is not live.

Yes, later.

Refresh

The caller’s information is old: another writer changed a value, the instance is gone, or another worker took the Operation.

The consumer, at run time.

After it reads the state again.

Refused

The tool and the request are correct, but a rule of the domain does not permit it: a SHACL shape, the OGM’s check against the ontology, a handover precondition.

No, not before the state changes.

Fix the call

The caller used the API incorrectly: an argument type, the IRI syntax, a mode, a malformed query.

The consumer’s developer.

No.

The map#

A solid arrow means that the type tells the action. A dashed arrow means that the type alone does not tell it: the consumer must read the message, and that is interpretation. Each dashed arrow is a gap, and Gaps: where the type does not tell the action lists them. A type with a dashed border has at least one gap.

Gaps: where the type does not tell the action#

  1. The interface’s error answers (closed in interface 2.3). Every error answer of the store is a TripleStoreResponseError with the store’s HTTP status in status, and a 401 and a 403 have a type of their own. A caller does not read the message to tell them. Fetching a graph and listing the datasets raise these types too, and no longer return None. The type’s action is Repair, also for a 400 or a 5xx, and a 401 can also come from a token that expired during a long run, because the interface does not log in again.

  2. Transport errors (closed in interface 2.3). An unreachable store, a timeout and a dropped connection raise TripleStoreUnavailableError, chained to the HTTP client’s error. A consumer no longer imports the HTTP client to catch them. An error of a request that the client could not build, such as an invalid URL, still crosses the border raw.

  3. The OGM’s ValueError (closed in OGM 0.4). The OGM’s own errors have the base OGMError and one category per action: OGMDataError (Refused, for example a required property is missing), OGMOntologyError (Repair, a property has no rdfs:range), OGMUsageError (Fix the call, two changes name the same instance) and OGMNotFoundError (Refresh, the class of an instance cannot be found). Each category is also a ValueError, so a handler of the built-in keeps working. A ValueError that is none of the categories is Repair.

  4. The middleware’s ValueError and RuntimeError (Repair closed in middleware 0.3) cover Fix the call, mostly, and also Refresh and Retry. The middleware’s Repair conditions, such as a missing store variable or an unknown mode, raise DeploymentValueError or DeploymentRuntimeError. Each is a subtype of DeploymentError and of the built-in that the condition raised before, so an except ValueError or except RuntimeError still catches it.

  5. The middleware’s OperationResolutionError (closed in middleware 0.3). It raises OperationReceiverUnavailableError (Retry) when a Workflow realizes the Capability but no Service of it is live now, and CapabilityNotRealizedError (Repair) when no Workflow realizes the Capability. Both are subtypes of OperationResolutionError.

  6. The middleware’s NotificationUndelivered (closed in middleware 0.3). It raises NotificationReceiverUnavailableError (Retry) when the resource is not live or did not take the notification, and NotificationReceiverAmbiguousError (Repair) when the resource has more than one live Service. Both are subtypes of NotificationUndelivered.

  7. The middleware’s REST routes answer 500 for every error, with the message as the detail. A remote consumer cannot tell the action.

  8. The middleware’s PossessionSwitchConflict replaces the interface’s PreconditionFailedError, which is its cause, and it is not a subclass of it. A consumer that catches PreconditionFailedError misses a handover conflict.

Errors that are logged, not raised#

Some handlers log an error and do not raise it. They are not paths to a consumer:

  • Background tasks with no caller, such as a domain callback or a notification handler. The graph records the outcome, for example the status failed, and the log holds the trace.

  • Observer hooks of a commit. A hook that raises does not change the result of the write. A refusal of the write itself is raised again.

  • An error transition that fails. The original error is raised, and the failure is added to it as a note.

  • Rendering and diagnostics: dashboard boxes, the log handler, pretty printing, the cancel of a background loop, and optional imports.

The next releases close the open gaps. Interface 2.3 already closes gaps 1 and 2 and the import path of “Paths that give no error”, OGM 0.4 closes gap 3, and middleware 0.3 closes gaps 5 and 6 and the Repair part of gap 4. Each change below is planned for the release that the table names.

A write whose connection drops after it was sent, or that times out, raises TripleStoreUnavailableError. The interface never sends a write again. A retry by the caller is safe for two reasons:

  • A checked write refuses a second application with PreconditionFailedError.

  • An insert or an import repeats as a no-op, because a graph is a set. The exceptions are blank nodes, which a second insert creates again, and a raw update that the caller writes itself.

The middleware’s HTTP statuses#

The middleware’s own routes, the parameter routes and the dashboard routes, will answer a typed error with the status of its action:

Action

Status

Repair

500

Retry

503

Refresh

409, or 404 when the addressed instance does not exist

Refused

422

Fix the call

400, also for a request that fails validation

The body of every error answer will have three fields: error, the type name; detail, the original message; and report, the raw store report or null. A bare built-in, such as a ValueError, will answer 500, because its type does not tell the action. No answer will carry a Retry-After header.

The routes that the framework generates do not follow this map. Its read routes on the datamodel answer 400 with a message of their own, and its workflow routes answer 409 for any RuntimeError. The served datamodel mounts no write route, so a write verb on it answers 405.
