kapps_semantic_middleware#

Let a piece of Python running on or beside a shopfloor resource expose what it can do through an RDF knowledge graph — and let other instances discover and invoke that capability through the graph, rather than through hardcoded network addresses.

A resource’s state is described in the graph as a protocol-interface parameter. The middleware wires that description to the real device: it discovers peers, serves them over REST, and keeps the graph and the device in step.

pip install kapps-semantic-middleware

Python 3.12 or newer. Nothing else is required to use the library.

Run the examples#

The scenarios and the factory demo need a few more packages and a running triple store. One extra covers the packages:

pip install "kapps-semantic-middleware[examples]"

Run kapps-examples to copy the runnable files out of the installed package into a directory you own — a notebook inside site-packages cannot be opened, edited or re-run. The path is relative to your current working directory:

kapps-examples ./kapps-examples
cd kapps-examples

You now have scenario 1 and scenario 2 (each as a .py and a .ipynb), the seed data they load, and a docker/ directory. Add the [notebooks] extra if you want to open the .ipynb files in Jupyter; the .py versions run with [examples] alone.

Start a GraphDB#

Docker is needed for the examples and the demo, never for the library itself.

cd docker
docker compose up -d

GraphDB comes up on http://localhost:7200 and the kapps-demo repository is created for you. This works the same on Linux, macOS and Windows.

Then point the library at it:

Linux and macOS:

export TRIPLESTORE_URL=http://localhost:7200
export TRIPLESTORE_USERNAME=admin
export TRIPLESTORE_PASSWORD=root

PowerShell (current session only):

$env:TRIPLESTORE_URL = "http://localhost:7200"
$env:TRIPLESTORE_USERNAME = "admin"
$env:TRIPLESTORE_PASSWORD = "root"

cmd.exe (current session only):

set TRIPLESTORE_URL=http://localhost:7200
set TRIPLESTORE_USERNAME=admin
set TRIPLESTORE_PASSWORD=root

To persist across sessions on Windows, use setx instead of set. setx does not affect the shell that runs it — open a new shell after running it.

Three variables, not four. TripleStoreEndpoint.from_env() in kapps_triplestore_interface also reads TRIPLESTORE_DATASET, and your own code may well use it — but nothing here does. The examples and the demo name the dataset kapps-demo in code, and the test suite names its own. A TRIPLESTORE_DATASET you already have set is ignored rather than obeyed, because these are the parts that wipe and re-seed whatever they connect to.

Never point TRIPLESTORE_URL at a store you care about. The examples and the demo clear the dataset they use on every run. docker compose down -v wipes the throwaway one; the next run re-seeds it.

Deprecated. The variables GRAPHDB_URL, GRAPHDB_USERNAME and GRAPHDB_PASSWORD are still read, each as the fallback of its TRIPLESTORE_* variable, and each use warns. The old names of kapps_semantic_middleware.credentials and kapps_semantic_middleware.seeding still work: graphdb_for, graphdb_env_present, REQUIRED_GRAPHDB_ENV, credentials_for, clear_repository and DEMO_REPOSITORY. Each use warns once and runs its successor: triplestore_for, triplestore_env_present, REQUIRED_TRIPLESTORE_ENV, endpoint_for, clear_dataset and DEMO_DATASET. A later release removes the old variables and names.

Run a scenario#

python scenario1_hello_world.py     # operation coordination through the graph
python scenario2_door.py            # direct state discovery and control

Run the factory demo#

A small factory as six real processes — one per mock PLC, one per middleware instance, and a controller that discovers every unit in the graph and drives it over REST. You watch it from a browser.

kapps-transferunit-factory

It serves a live status page on http://127.0.0.1:8080/. --units N sets how many TransferUnits run (two by default); --force clears the graph even when a live factory still holds a fresh heartbeat. Ctrl+C stops every process.

If you are writing code against this library, read AGENTS.md first. Several of its rules are constraints that do not appear in any type signature and fail by producing quietly wrong behaviour rather than an exception.

Questions#

Can I install it with uv? Yes. Run this instead of the pip install at the top, not after it:

uv add "kapps-semantic-middleware[examples]"

pip install answers externally-managed-environment. Debian and Ubuntu mark their system Python as externally managed, so pip refuses to write into it. Use a virtual environment:

python3 -m venv .venv
. .venv/bin/activate
pip install "kapps-semantic-middleware[examples]"

uv needs no such step — it creates and manages the environment itself.

Is [examples] really needed for the factory? Yes, and leaving it out does not look like an error. uvicorn and rdflib reach you anyway, as dependencies of something else; amqtt — the in-process MQTT broker each unit brings up — does not. Without it the launcher seeds the graph, the first middleware starts and prints its address, and then the mock PLC repeats a line like

broker at 127.0.0.1:18831 not ready yet ([Errno 111] Connection refused), retrying in 5.0s

for as long as you let it run. No traceback appears, and neither does Factory running. If you see that line, the extra is what is missing.

Status#

Usable, and still on a 0.x line: the scenarios and the factory demo run end to end, but the API may still move, and a minor bump may break you. CHANGELOG.md records what each release changed.

Contributing#

Development happens in a private repository and this one is the published half: it carries one commit per release and no ancestry, so there is nothing here to branch from.

Bug reports and questions are welcome as issues on this repository. A patch is welcome too – say what it changes and why, and it will be applied on the development side and credited in CHANGELOG.md for the release that carries it.
